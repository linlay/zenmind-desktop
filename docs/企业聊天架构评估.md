# 企业聊天架构评估

## 结论

`zenmind-im-server` 当前不拆分 SQLite。消息、附件绑定、会话序号和每个接收人的可靠事件
必须在同一事务提交；把 `messages` 与 `user_events` 拆到不同 SQLite 文件会失去原子提交，
增加双写补偿和恢复复杂度，却不会消除 SQLite 的单写者限制。

服务继续保持单活动实例、WAL、busy timeout、外键和短事务。达到扩容阈值时直接迁移
PostgreSQL、共享对象存储和跨实例事件总线，不设计多个 SQLite 文件的中间形态。

## 2026-07-27 sas01 只读基线

- 容器 `zenmind-im-server` 健康，宿主仅映射 `127.0.0.1:11956`。
- `PRAGMA quick_check=ok`，journal mode 为 WAL。
- 数据库 212 KiB，WAL 4 MiB，page size 4 KiB，57 个数据库页，无 freelist。
- 5 个用户、7 个设备、10 个会话、44 条消息、186 条 `user_events`，blob 为 0。
- 当前事件放大率约为每条消息/成员变更为每个可见成员保存一份可靠事件。现有体量远未达到
  SQLite 容量或写吞吐边界。4 MiB WAL 是默认约 1000 页 checkpoint 后复用的常见文件大小，
  不是异常增长。

## 稳定性措施与迁移阈值

生产监控至少记录数据库、WAL、blob 容量，写事务耗时，`SQLITE_BUSY` 次数，checkpoint
耗时，备份耗时，消息写入速率，活跃连接数，以及 `user_events/messages` 行数比。日志和
指标不得包含消息正文、文件名、邮箱、token 或用户 ID 标签。

出现下列任一持续现象时进入 PostgreSQL 迁移评审，而不是拆 SQLite：

- p95 消息提交超过 100 ms，或持续出现 `SQLITE_BUSY`；
- 单机写入持续接近 100 条消息/秒，群成员数导致可靠事件写放大明显；
- 在线备份或恢复时间超过可接受的 RPO/RTO；
- 需要两个以上活动服务实例；
- 单机本地磁盘不再满足容量、IOPS 或高可用要求。

`user_events` 是最可能先膨胀的表。现有 90 天清理应保留；后续可增加分批清理、被动
checkpoint、`PRAGMA optimize` 和只暴露聚合值的运行指标。不能把可靠事件异步写到另一个
数据库，否则消息已提交但事件缺失时会破坏断线补偿。

代码审计还发现两个需要在规模上升前处理、但当前数据量无需抢修的点：

- 每小时事件清理当前是一次无上限 `DELETE`；数据量大后应改为按主键/时间索引小批提交，
  避免长写事务阻塞消息。
- 会话摘要和 50 条历史的 hydration 存在按会话/消息继续查询附件与成员的 N+1 读取；
  先用 p95 延迟和 query 计数确认瓶颈，再合并为批量查询，不能通过拆库掩盖查询放大。

`VACUUM INTO` 能生成一致的数据库备份，但 blob 目录不是同一事务快照。生产备份应记录
数据库水位，并使用卷快照或“数据库备份 + blob 增量清单”形成可验证的一致恢复点。

## 文件与对象存储

服务端现有 `internal/blob.Store` 已把数据库元数据与文件字节分离。本地实现使用服务端
opaque key、私有权限、流式写入、SHA-256、原子移动和逐次成员权限检查；这已经是未来 S3
实现的正确边界。

S3 实现应保持相同语义：数据库只保存 opaque key；上传完成后才写 ready 元数据；绑定消息
与文件状态仍在数据库事务内完成；下载每次先验证当前会话权限，再由服务端流式代理或签发
极短期、单对象、只读 URL。不能把 bucket key 或长期公开 URL发给 renderer。

## 内网 IP 与局域网快传

默认不要求用户上报本机内网 IP。内网地址属于网络拓扑信息，多网卡、VPN、IPv6、NAT、
休眠与网络切换会使它快速失效；服务端观察到的来源地址也不能证明两台设备可直连。

局域网快传可以作为后续显式 opt-in 能力，采用“能力注册”而不是裸 IP 目录：

1. 用户主动开启“局域网快传”，Desktop 在随机高位端口启动仅局域网可达的临时 HTTPS 服务。
2. Desktop 向 IM Server 上报短 TTL 的设备 capability，包含候选地址、端口、协议版本、
   一次性公钥指纹和过期时间；不写聊天历史，不长期保留。
3. 发送方先通过正常 E2E 鉴权消息交换一次性 transfer offer，接收方确认后才尝试直连。
4. 文件按块传输并校验整体 SHA-256；会话密钥绑定双方用户、设备、文件和过期时间。
5. mDNS/候选地址直连失败、超时或用户未开启时，无感回退到现有 server relay。
6. macOS 与 Windows 分别处理防火墙、网络权限和休眠恢复；服务不得绑定公网接口。

第一阶段继续使用 server relay。只有当文件流量和跨公网延迟成为真实瓶颈，并完成威胁模型、
防火墙体验和失败回退测试后，才实现局域网快传。
