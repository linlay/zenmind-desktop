# 启动初始化与恢复

## 当前状态

Desktop 启动分为 Electron 壳准备、运行环境导入、状态初始化、核心服务准备和非核心运行时启动。核心服务启动由 `createStartupPipeline()` 协调，失败时进入 `degraded` 状态。

首次 bootstrap 涉及：

- `agent-container-hub`
- `identity-center`
- `agent-platform`
- `agent-webclient`

其中 `agent-container-hub` 是 install-only startup service：首次启动准备安装和初始化，但不作为强启动依赖。

企业聊天是独立的非核心客户端 runtime：它只连接外部
`zenmind-im-server`，不进入内置服务安装、恢复或启动卡。`non-core-ready`
阶段按 `enterprise-im.json -> enabled` 启用，真正换票和连接由完整企业 SSO 状态触发。Cookie SSO 启动恢复处于 `temporarily_unavailable` 时，企业聊天和 Tunnel Hub 暂不启动，Kanban、Market 与 Website 也不得消费旧 token；恢复到可确定状态后再启动或刷新这些消费者。

## 核心流程

启动阶段：

```text
booting
-> platform-preflight
-> runtime-env
-> runtime-env-ready
-> desktop-state-ready
-> shell-ready
-> core-services-starting
-> core-ready
-> non-core-ready
```

`desktop-state-ready` 内的 SSO 恢复顺序：

```text
initializeUserDataRootsAndSettings()
-> restoreDesktopSsoSession()
-> registerMainIpcHandlers()
-> createWindow()
-> startupPipeline.run()
```

进入 `runtime-env-ready` 前，Desktop 先按实际品牌 runtime root 处理内置环境包。首次或缺失环境继续完整导入 env.zip；已有环境则比较
`state/desktop/env-resource-sync.json -> desktopVersion`，任意版本变化（包括降级）只同步
`agents`、`registries`、`skills-center`、`tools`。同步失败不提交版本标记，并复用 env-import-required
降级流程阻止核心服务启动；产品清单明确 `bundled=false` 时跳过该阶段。

Cookie SSO 恢复必须在主窗口创建前完成一次最多 5 秒的上游 session 校验。磁盘 `sso-session.json` 只是候选状态；校验成功后强制换取新 access token、同步写入专用 SSO partition 与 default session 并刷新存储，之后才能发布已登录。明确失效会清理 canonical 凭据和已知 Cookie；断网、超时、`429`、`5xx` 保留文件和上游 session Cookie、移除派生的旧 `access_token` Cookie，运行态保持未登录，等待状态查询或 5 分钟定时器单飞重试。

核心服务准备顺序：

```text
Prepare:
agent-container-hub
-> identity-center
-> agent-platform
-> agent-webclient

Start:
identity-center start + verify running
-> parallel(agent-platform start, agent-webclient start)
```

在普通 Prepare 之前，Desktop 只比较仓库根 `VERSION` 对应的 Desktop 版本标记，不读取四个服务 manifest 的版本。`state/desktop/service-config-version.json` 缺失且不是首次全新安装时，按 `legacy -> 当前版本` 处理；标记与当前版本字符串不同（包括降级）时，按 `agent-container-hub -> identity-center -> agent-platform -> agent-webclient` 串行停止旧进程、安装当前服务程序并调用 reset deploy。首次安装和同版本重启不执行 reset。

升级中使用 `state/desktop/service-config-upgrade.json` 持久化进度。reset deploy 由服务脚本把原配置原子移动到 `config/service-backups/<from>-to-<to>/<service-id>/`，再从当前包模板重建；Desktop 不读取服务配置内容。四项 reset 完成后继续现有核心启动与健康检查，只有 `identity-center`、`agent-platform`、`agent-webclient` 均验证 running/health，才写入新版本标记并删除事务日志。

启动界面：

- 核心服务处于读取、安装、初始化或启动阶段时，Desktop 使用全窗 `StartupLoadingScreen` 覆盖层显示居中卡片。卡片列出 `identity-center`、`agent-platform`、`agent-webclient` 三项状态、已就绪数量和总体进度。
- 45 秒后尚未完成时，卡片显示「启动较慢」并提供「重新检查」和「进入控制中心」；启动恢复失败或恢复完成后任一核心服务不再 running 时，卡片显示失败信息及相同恢复入口。
- env.zip 导入使用独立导入层，不与启动卡同时显示；进入设置或控制中心处理故障后，本次启动卡允许保持关闭。
- 主窗口已经以“SSO 未配置”状态创建后再手工导入 env.zip 时，若 bootstrap 生成了合法的
  `config/desktop/sso.json`，运行态只切换为“已配置、未登录”并广播刷新，使账户菜单立即出现登录入口；
  该刷新不得读取或恢复磁盘上的 session、user-info 或 access token 候选，用户仍需主动登录。
- 核心服务与导航智能体都就绪后，Desktop 继续既有的默认 Chat 自动导航。
- `shell-ready` 阶段会先创建 Electron 托盘，再启动核心服务恢复；即使核心服务进入 `degraded`，Windows 右上角关闭按钮仍只隐藏主窗口，托盘图标保持可见。
- Windows 用户通过托盘菜单重新打开主窗口、进入设置或选择「退出」；启动失败页不提供额外的应用退出按钮。
- 纯色居中加载页是无选中内容的兜底，而不是核心服务启动进度页：根路由 `/` 尚未进入 Chat，以及 `/webs` 没有选中 Site/Browser 时，主内容区显示加载动画和「正在加载核心组件」。选择 Chat、Site 或其他功能页面后不显示该兜底页。
- 兜底页只覆盖 Desktop 主内容区；macOS 和 Windows 标题栏拖拽区域保留，且主内容区不保留默认外边距或卡片边框。

关键依赖：

- `agent-platform` 的 deploy 阶段接收 `identity-center` public key 源文件，并由自身 `deploy.sh` 写入本服务配置目录。
- `agent-webclient` 的 deploy 阶段只初始化本服务 `.env`；host-managed start 阶段通过 `lifecycleArgs.start --base-url` 接收 `agent-platform` base URL，并由 Desktop main process 托管静态前端和代理。
- Start 阶段先确认 `identity-center` running，再启动 `agent-platform` 和 `agent-webclient`。

## 配置与接口

- 启动 phase 定义在 `STARTUP_PHASES`。
- 默认恢复服务来自 `DEFAULT_STARTUP_SERVICE_IDS`。
- `state/desktop/last-running-services.json` 保存下次启动恢复列表。
- `state/desktop/bootstrap.json` 保存一次性 desktop-init 应用结果。
- `state/desktop/env-bootstrap.json` 保存 env.zip 导入结果。
- `state/desktop/env-resource-sync.json` 保存四类内置环境资源最近一次成功同步的 Desktop 版本与统计。
- `state/desktop/service-config-version.json` 保存最近一次成功完成核心启动验证的 Desktop 版本。
- `state/desktop/service-config-upgrade.json` 只在首次安装尚未完成或版本配置重建事务未完成时存在，用于失败续跑。
- `config/desktop/service-lifecycle-args.json` 保存从 `desktop-init.json` 拆出的服务脚本附加参数。
- Desktop 版本变化时，`service-port-defaults.json` 保留合法端口、非法端口回退到当前 Desktop 默认值；`service-lifecycle-args.json` 被严格重写，只保留 Identity issuer、Platform 模型 deploy 参数和 WebClient `--base-url`。WebClient 缺少合法 base URL 时，使用当前 Agent Platform 默认端口生成 loopback URL。
- `config/desktop/desktop-action-bridge.json` 保存从 `desktop-init.json` 拆出的 Desktop 自身 HTTP action bridge 端口。
- `config/desktop/enterprise-im.json` 完整保存 `desktop-init.json -> enterpriseIm` 的 `enabled` 与 `baseUrl`；loopback 可使用 HTTP，远端必须使用 HTTPS。再次应用 desktop-init 时两个字段都覆盖现有值。
- `config/desktop/help.json` 保存从 `desktop-init.json -> help.url` 拆出的匿名 Help 网站地址；loopback 开发地址可使用 HTTP，远端必须使用 HTTPS。Help 配置不包含 token、Cookie 或 SSO 参数。
- `config/desktop/sso.json` 原样接收 `desktop-init.json -> sso.avatarCache` 的简化配置
  `{ enabled, trustedOrigin }`；provider allowlist、下载大小和超时由官网/Desktop 代码策略控制。
- `config/desktop/assistant.json` 中的 `bootstrapAgentKey` 与 `bootstrapChatId` 描述初始化智能体和预置会话；未提供预置会话时可省略 `bootstrapChatId`。包含 bootstrap 的环境还携带 `<bootstrapChatId>/desktop-overview.png` 和 `<bootstrapChatId>/desktop-sidebar-actions.png`，分别作为首条介绍消息中的主界面分区图与侧边栏操作图。
- runtime 根目录的一次性 `provider-register.json` 可用 JWT Grant 兑换 Transit Hub API key。仅当 provider 的 `apiKey` 缺失、为 `null` 或空白字符串时才补齐；任何非空值均不得覆盖，成功后立即清理含 JWT 的一次性文件。
- `desktop-init.json` 的 `assistant.defaultChatAgentKey` 记录初始化完成后的正式 Chats 默认智能体；该值必须来自 agent-platform `scope=nav`，bootstrap 运行时覆盖不得写回该字段。
- `desktop-init.json` schema v2 可通过 `webs.items` 一次声明多个 Website 与 WebApp。Website 在条目内声明 `url`、`label` 和可选 `copilotAgentKey`；WebApp 条目只声明 `kind=webapp` 与 `id`，包固定从同级 `desktop-init/sites/<id>/` 读取。新 WebApp 包必须满足 Manifest v2，`desktopBridge` 只保留 `{ "version": 1 }`。需要选择智能体时，在 `userConfig.fields` 中声明 `type: "select"`、`source: "desktop.agents"` 的字段，用户选择的 Agent Key 按该字段的 `name` 保存在包外用户配置中；固定功能提示词写入 `appConfig`，可编辑补充要求通过 `userConfig` 字段定义，WebApp 将二者与本次输入组合。
- `desktop-init.json` 只接受 schema v2 的 canonical 字段：`assistant.defaultChatAgentKey`、`profile.assistant.copilot`、`profile.navigation.webOrder`、顶层 `kanban`、`enterpriseIm.enabled`、`enterpriseIm.baseUrl`、`help.url` 和 `webs.items`。企业 IM 不接受旧 `imServer` 或 `profile.general.enterpriseChatEnabled`，也不迁移旧 `im-server.json`；其他 retired Profile、Kanban、Website、Help 或 assistant 字段同样不迁移。
- Sites 是一次性 seed：只有不存在 `state/desktop/bootstrap.json` 的新 runtime 才安装并按 `webs.items` 顺序写入首次侧栏顺序。普通重启、升级以及对已有 Desktop 手工导入 env.zip 时使用 preserve 模式，不补装、不覆盖、不恢复用户删除的 Site，也不改变用户顺序。
- 用户明确“还原 env.zip”时，当前 runtime 先整体移动为时间戳备份；新 runtime 尚无 bootstrap state，因此下次启动会重新执行 Sites seed。重置 IPC 返回 `restartRequired=true`，重启前不在旧进程中展开 Site seed。
- Site seed 在任何写入前先完整校验：Website 的 id/URL 唯一性与 14 个数量上限、WebApp 安全 id、固定目录、manifest id 一致性、frontend/backend 路径和符号链接。任一项失败时该批 Sites 不留下部分安装。
- 安装或 preserve 处理完成后删除 runtime 中的 `desktop-init/sites` staging；原始 env.zip 仍保留在 `data/env-initial/`。bootstrap state schema v2 的 `websReport` 记录 initialize/preserve 模式、安装/跳过项与警告。
- `<runtimeRoot>/owner/OWNER.md` 是 Chats 首次初始化的唯一完成标志。Desktop 只检查该路径是否为普通文件，不读取或校验内容，也不要求 `owner/BOOTSTRAP.md` 已删除；主进程通过 `fs.watchFile` 监听精确路径，创建或删除时广播最新状态，stat/读取失败一律按不存在处理。
- 配置了 `bootstrapAgentKey` 时采用严格模式：OWNER 不存在只选择 bootstrap，OWNER 存在只选择 `defaultChatAgentKey`；目标 agent 尚未出现在 nav 时保持等待，不跨模式降级。`defaultAgentAvailable` 只表达 nav 可用性，不再代表初始化完成。未配置 `bootstrapAgentKey` 的普通环境继续使用既有默认 Chat agent 逻辑。
- Renderer 必须等待 assistant settings、nav agents 与 bootstrap state 全部加载后才执行首次自动导航，避免正式 agent 首屏闪现。OWNER 不存在且 bootstrap 可用时，每个 Desktop 启动会话只自动选择一次预置 Chat，不自动发送消息或创建 run；用户随后进入 Help 或其他页面时不会被再次拉回。OWNER 出现后立即清除 bootstrap Chat、Help 黄框、引导卡和气泡；若当前仍停留在 bootstrap Chat，则本次启动仅一次进入默认 agent 新会话，位于 Help、Settings 等非 Chat 页面时不强制跳转。初始化状态不根据 agent 可用性或 run 终态推断。
- env 导入继续采用缺失文件复制语义，不覆盖已有 `chats.db`。已有数据库无法索引预置会话时，Chats 自动打开 bootstrap 新会话并显示同名黄色降级入口，不由 Desktop 修改服务自有数据库。
- bootstrap 接管 Chats 期间，预置 Chat 和 Help 入口保持黄色引导框；侧栏恢复可关闭的新手引导卡和 60 秒浮动气泡，`OWNER.md` 出现后立即清除全部引导状态。初始化文字、主界面分区图、侧边栏新建 Chat / Project / Site 指引和下一步均由 WebClient 原有 Chat 主区域回放和渲染，Desktop 不提供另一套初始化内容区。

## 启动初始化硬性规范

- Desktop 只负责编排 install、deploy、start、stop、verify；不得修复、迁移、补全或推导内置服务 `.env` 和服务自有配置。
- 内置服务配置默认值、旧 env 清理、配置迁移、runtime 目录初始化和服务间 URL 写入，都必须在各服务自己的 `deploy.sh` / `deploy.ps1` 中完成。
- `deploy`、`start`、`stop` 参数不能混用。`deploy` 只接部署期配置落盘参数；`start` 只接启动期 layout、端口和 daemon 参数；`stop` 只接定位 pid / state 所需的最小参数。
- Desktop 不为内置服务追加通用 deploy layout flags。每个内置服务的 deploy 参数必须在 service manager 中显式列出，并由 bundle validation 校验。
- 四个核心 deploy 统一支持 reset 参数：`--desktop-config-reset`、`--desktop-config-backup-dir <absolute-path>`、`--desktop-version-from <version|legacy>`、`--desktop-version-to <version>`。Desktop 只传递这些上下文；模板生成、旧字段清理和凭据白名单迁移仍归服务脚本。

当前内置服务生命周期参数 contract：

| Service | deploy | start | stop |
| --- | --- | --- | --- |
| `agent-container-hub` | `--output-dir` | `--config-dir`、`--data-dir`、`--state-dir`、`--log-dir`、`--bind-addr`、`--daemon` | `--state-dir` |
| `identity-center` | `--output-dir`，以及 `service-lifecycle-args.json` 中声明的 `--auth-issuer` | `--config-dir`、`--data-dir`、`--state-dir`、`--log-dir`、`--port`、`--daemon` | `--state-dir` |
| `agent-platform` | `--output-dir`、`--ap-runtime-dir`、`--container-hub-base-url`、`--public-key-source-file`，以及模型类 deploy 参数 | `--config-dir`、`--state-dir`、`--log-dir`、`--port`、`--daemon` | `--state-dir` |
| `agent-webclient` | `--output-dir` | host-managed，不执行 bundle start；Desktop 消费 `service-lifecycle-args.json` 中的 `--base-url`，端口由 Desktop defaultPort 管理 | host-managed，不执行 bundle stop |

reset deploy 只允许按各服务自己的凭据白名单迁移必要凭据；旧端口、路径、Engine、YAML、自定义启动参数及其他历史配置一律不复制。Desktop 不知道、也不维护服务目录内的文件名和字段清单。

## 约束与注意事项

- Prepare 阶段保持串行，避免配置、密钥和端口依赖乱序。
- 如果 `identity-center` prepare/start/verify 失败，不启动后续依赖服务。
- 配置重建或核心健康检查失败时不自动回滚：新失败配置、原始备份和事务日志全部保留，启动进入 degraded。下次启动从日志续跑；再次 reset 前服务脚本把上次失败配置保存为同事务下的临时 `.failed` 诊断副本，且不得覆盖原始备份。成功后删除诊断副本和更早备份，只保留最近一次成功升级前的备份。
- `agent-platform` 和 `agent-webclient` 的 sibling start 失败互不取消。
- 首启和手工 env.zip 导入继续只复制缺失文件，不覆盖已有 agent、provider、owner 等 seed。
- 覆盖安装的版本资源同步使用固定白名单。`agents/<agentKey>`、`skills-center/<skillKey>`、
  `tools/<toolKey>` 以一级资源为单位：目标已存在即整项跳过，目标不存在才完整递归加入。
  `registries/**` 则按 env.zip 内文件路径强制覆盖或新增，但不删除包中没有的用户 Registry。
  其他 runtime 内容不参与同步；文件/目录冲突和 runtime 内符号链接父目录都按失败处理。
- 版本资源同步只为新复制的 `.sh` 设置 `0755`，不会修改已跳过 Agent、Skill 或 Tool 内的脚本权限。
  首启/手工 env.zip 导入仍保持既有脚本权限恢复语义。
- `env.zip` 导入在 macOS/Linux 会将其中所有 `.sh` 脚本恢复为 `0755`，包括因“只复制缺失文件”而跳过的既有脚本；Windows 的 `.ps1` 不使用 POSIX 权限位，必须由 PowerShell（`-NoProfile -ExecutionPolicy Bypass -File`）作为解释器执行。
- Site 未配置专属 Copilot 时不在安装阶段写入默认 key。打开 Site 时按 `site.copilotAgentKey -> assistantSettings.desktopHelperAgentKey -> DEFAULT_DESKTOP_HELPER_AGENT_KEY` 动态解析，所以修改 Desktop 默认 Copilot 后无需改写 Site manifest。
- `zenmind-im-server` 不属于 Desktop built-in service；服务不可达只影响聊天浮层，不能阻塞 `core-ready` 或把启动恢复标记为失败。
