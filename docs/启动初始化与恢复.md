# 启动初始化与恢复

## 文档定位

本文描述 Desktop 从 Electron 启动到可用状态的阶段、依赖顺序和恢复策略。phase 常量、状态文件、超时、脚本参数和界面文案以源码及测试为准。

## 启动目标

启动流程需要同时满足：

- 在创建业务界面前确定品牌、数据根和认证候选状态。
- 严格按依赖顺序准备核心服务，避免配置、密钥和端口乱序。
- 把首次安装、版本变化、手工导入和普通恢复区分为不同事务。
- 失败后保留可续跑状态，不用猜测或隐式修复掩盖问题。
- 核心服务失败可以进入 degraded；非核心能力不能阻塞 Desktop 壳与诊断入口。
- 容器引擎等可选能力的探测必须异步、限时并可降级，不能占用 Electron 主线程或延迟核心服务就绪。

## 阶段模型

主进程先冻结首次安装与运行根存在性快照，并完成单实例及安装器退出分流，再在 Electron ready 之前固定品牌数据根 state 层的 Chromium profile。`userData` 与 `sessionData` 必须指向同一 profile，进程运行期间不得重新定位。首次安装的旧根迁移和运行环境导入必须先于会创建 Session 的协议处理器注册，避免迁移已打开的浏览器数据文件。

```text
平台与 Electron 预检
  -> 解析运行环境和 Desktop 数据
  -> 恢复可信认证状态
  -> 创建 Shell、IPC、窗口与托盘
  -> 准备并启动核心服务
  -> 启动非核心 runtime
  -> 发布可用或 degraded 状态
```

核心服务的准备顺序固定为：

```text
agent-container-hub
  -> identity-center
  -> agent-platform
  -> agent-webclient
```

`agent-container-hub` 只参与安装和准备，不是 Desktop 可用的强启动依赖。`identity-center` 必须先通过运行验证，随后 `agent-platform` 与 host-managed `agent-webclient` 才能并行进入运行状态。

企业聊天、Kanban、Market、Tunnel、Web surface 和助理桥属于非核心 runtime。它们在 Shell 可用后启动，并根据配置、SSO 和依赖服务状态独立刷新或降级。

## 四类启动事务

### 全新安装

Desktop 校验并导入完整运行环境，应用一次性 `desktop-init`，安装核心服务和初始 Site，然后写入完成状态。任何输入在写入前必须整体验证，不能留下半套运行环境。

全新安装的 UI 引导只以进程启动前品牌运行根下的 Desktop 数据根是否存在为准。主进程必须在创建该目录前冻结判断结果，并通过进程内一次性 IPC 交给 renderer；不为引导另写磁盘完成标记。`owner/OWNER.md` 是可选用户资料，缺失、创建或删除都不改变启动分类和导航。

首次引导按固定顺序选择目标：已索引的 seed Bootstrap Chat、Bootstrap Agent 的新 Chat、默认 Chat Agent 的新 Chat。seed Chat 被用户删除后不恢复，覆盖安装和版本升级也不重写用户 Chats。除这一次首次导航外，侧边栏、全局搜索和空路由的新 Chat 始终使用配置的默认 Chat Agent；用户离开引导后不自动拉回。

### 普通启动

Desktop 读取已有状态，恢复上次应运行的服务并校验健康状态。普通启动不重新应用 seed，不覆盖用户已修改或删除的资源。

### Desktop 版本变化

版本变化以 Desktop 根版本为触发条件。Desktop 先固定并校验升级输入，再更新自己拥有的 canonical 配置，然后依次调用各服务的 reset deploy。服务内部配置重建与领域资源迁移由服务脚本负责。

升级事务必须持久化进度。失败时保留原始备份、新失败现场和 journal；下次启动从已验证输入续跑，不能自动猜测回滚成功。

### 手工导入或还原

手工导入是用户显式触发的领域资源更新，不等同于自动版本升级。还原则先隔离旧运行根，再建立新的运行环境；两者不能复用普通启动的隐式兼容路径。

## 认证恢复顺序

SSO 候选状态在主窗口创建前由 main 按当前 SSO 配置校验。浏览器会话默认使用 Cookie 校验，显式配置的 Bearer 恢复使用保存的 token 调用同源接口；不能按品牌猜测或自动切换恢复凭据。磁盘文件不能直接证明当前已登录；只有上游校验、token 换取、身份确认和 Electron session 写入全部成功后，才发布 authenticated。

明确失效会清理凭据；网络、限流和临时服务错误只进入可重试的未认证状态，不把旧 token 继续提供给 Website、Kanban、Market、企业聊天或 Tunnel。认证细节见[鉴权SSO与TokenBridge](鉴权SSO与TokenBridge.md)。

## 登录后绑定模型凭据

运行环境中的 `provider-register.json` 是自动获取模型凭据的唯一策略入口。文件缺失表示不自动获取，不主动删除已有 Key。两种模式不自动回退；无显式模式的旧文件沿用原 Grant 行为，非法配置必须报错。

登录模式的环境部署与身份基础准备不依赖模型 Key；在启动或复用 Agent Platform 前，main 必须校验当前登录并完成用户设备绑定。未登录时发布登录门禁，Shell 的登录、控制中心、日志和退出仍可使用；登录成功后重新进入串行服务启动事务。登记文件成功后保留，不能按一次性 Grant 的语义删除。即使 Provider 已有 Key，也不能跳过当前账号绑定。

恢复时不能直接复用加载着旧账号凭据的存活模型进程。身份失效时立即使在途登记 generation 失效，并通过服务变更队列停止受管消费者、清除选定 Provider 的旧 Key；新登录的启动事务排在清理之后。网络失败保留策略供重试，不放行旧身份。手动启动与自动启动执行相同门禁。

## Desktop 与服务边界

Desktop 负责安装资源包、分配目录、调用 `deploy/start/stop`、传递已定义的生命周期上下文并验证状态。Desktop 不解析、合并、修复或生成内置服务的 `.env`、YAML 和领域数据。

服务负责自己的默认配置、旧键清理、配置迁移、runtime 资源同步和服务间配置落盘。Agent Platform 额外负责 Agent、Skill、Tool、Team、Registry 和 Provider 等平台领域资源。Provider API Key 申请由 Desktop 主进程按运行环境登记文件的显式模式完成：旧 Grant 流程只填充缺失 Key，登录模式在可信登录后领取当前用户与设备绑定的 Key，并替换登记文件选定的受管 Provider 凭据；登记流程不承担 Provider 配置迁移，网络与凭据边界见[鉴权SSO与TokenBridge](鉴权SSO与TokenBridge.md)。

## 失败与恢复

- Windows 程序数据清理保留 Electron 持有的单实例锁文件，它不属于可替换服务资源；macOS 清理规则不变。程序数据版本标记仅在应清理资源全部处理成功后写入，真实清理失败仍须保留重试语义。清理结果在数据根初始化完成、文件日志接入后记录，包含旧/新版本、已删除路径和失败路径。
- 输入或 bundle 预检失败必须发生在停止现有服务之前。
- `identity-center` 失败时不继续启动依赖它的服务。
- sibling 服务启动失败互不伪装为成功，最终状态独立记录。
- Container Hub 的 Docker / Podman 探测失败只影响自身能力，不改变核心启动顺序和 `core-ready` 判定。
- 核心恢复失败进入 degraded，并保留控制中心、日志和重试入口。
- 非核心 runtime 失败只影响自身，不改写核心服务状态。
- 只有核心服务达到定义的健康条件后，才能提交版本或启动事务完成标记。
