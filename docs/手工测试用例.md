# 手工测试用例

## 环境准备

```bash
npm install
npm run sync:assets
npm run dev
```

如需测试容器服务，先确认 Docker 或 Podman 可用。打包测试前先确认 `BRAND`、`ENV_ZIP`、`DEMO` 等环境变量符合目标场景；启用 Demo 时同时配置 `WEBAPP_BUILDER_SKILL_DIR`。

## 启动与核心服务

1. 启动 `npm run dev`。
2. 进入控制中心，确认 `identity-center`、`agent-platform`、`agent-webclient` 可见。
3. 首启场景下确认 `identity-center` 先 running，随后 `agent-platform` 和 `agent-webclient` 启动；服务准备期间显示全窗居中的 `StartupLoadingScreen` 卡片，包含三个核心组件的状态、已就绪数量和进度条。
4. 将核心服务启动时间延长至 45 秒以上，确认卡片显示「启动较慢」、「重新检查」和「进入控制中心」；使启动恢复失败或在恢复完成后停止任一核心服务，确认卡片显示失败信息，进入控制中心后可查看服务详情且启动卡不遮挡设置页面。分别在 macOS 与 Windows、亮暗主题和窄窗口下确认卡片可完整滚动、遮罩连续。
5. 在核心服务已就绪时停留于根路由 `/`，确认主内容区显示纯色「正在加载核心组件」兜底页；关闭最后一个 Site/Browser 并进入 `/webs` 时确认 WebView 已卸载，且主内容区显示「暂无打开的网站应用」，不再显示核心组件加载提示。随后打开 Chat、Site、设置、市场或看板，确认空状态不覆盖所选内容，标题栏拖拽区域保持正常。macOS 切换到其他应用使 Desktop 失焦后，直接在标题栏按下并拖动，确认第一次按下即可同时激活并移动窗口，无需再次点击；Windows 保持既有首次拖动行为。
6. 使用包含 `desktop-init.json`、bootstrap agent、seed JSONL、seed `chats.db`、`<bootstrapChatId>/desktop-overview.png` 和 `<bootstrapChatId>/desktop-sidebar-actions.png` 的干净 env.zip 首启，确认自动打开并选中“点击我完成初始化工作”，且从 Chats 侧栏点击该 bootstrap 会话可正常进入；仅回放 assistant 自我介绍且没有创建 run。欢迎语完全在 WebClient 原有 Chat 主区域显示，先展示标有黄色框的导航 / 内容 / 副驾或概览分区图，再展示新建 Chat、Project、Site 的侧边栏指引，图片通过既有资源接口加载。Bootstrap Chat 和 Help 均显示黄色引导框，设置菜单自动展开，并可看到完整新手引导卡与浮动气泡。
7. 在 macOS/Linux 检查导入后的任意 `.sh`（包括 `agents/bootstrap/bootstrap.sh`）权限为 `0755`，可直接以绝对路径启动；将某个已导入 `.sh` 人工改为 `0644` 后再次导入同一 env.zip，确认脚本内容仍不覆盖且权限恢复为 `0755`。Windows 对应的 `.ps1` 应使用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <absolute-path>` 启动。
8. 从初始化 Chat 主动进入 Help 或其他页面，确认本次启动不再强制跳回；重启且 bootstrap 仍存在时确认重新自动选择同一 Chat。发送消息后确认正常创建 run、接收 SSE 和处理 awaiting，profile 的正式默认 Agent 未被改写。
9. agent-platform 的 nav 列表出现 `defaultChatAgentKey` 后，确认黄色引导和引导卡立即消失、普通 Chats 列表不再显示 bootstrap 会话；当前停在 bootstrap Chat 或再次通过旧链接打开该 Chat 时，Desktop 都自动进入准确的默认智能体新会话，无需等待或接收 `run.complete`。已有 `chats.db` 时确认用户数据不被覆盖；默认智能体尚未出现时，Desktop 仍可打开 bootstrap 新会话并选中黄色降级入口。
10. 查看服务详情，确认 PID、日志路径、端口、web URL 展示正常。
11. 停止和重启 `agent-platform`，确认状态和日志更新。

## 前端嵌入与认证

1. 打开 `agent-webclient` 页面，确认 webview 正常加载。
2. 检查所有 agent-webclient URL 都不包含 `desktopAuthContext`；聊天和 Copilot 分别包含 `wsSource=desktop-chat` 和 `wsSource=desktop-copilot`。
3. 打开 Agents、Archives、Automations、Memory 和 Registries，确认 URL 不包含 `wsSource`，Network 中没有 `/ws` 连接。
4. 在 agent-webclient 中触发需要 token 的请求，确认没有手动输入 token。
5. 停止并重启 `agent-platform`，确认旧 token 被丢弃，聊天 HTTP/WS 通过 Token Bridge 恢复。
6. 打开 `identity-center` 管理页，确认进入 `/admin/`。
7. 打开 `agent-platform` monitor，确认 access token 注入后页面可访问。
8. CuteJ 登录后确认 `browserSession` 请求 `/oauth2/auth` 返回 200/202，并立即生成 `state/desktop/sso-session.json`；文件为 schema v2 且不包含 `user`、Cookie 或 access token。
9. 确认 `/oauth2/auth` 的已验证响应头包含稳定用户 ID 后立即生成 `sso-user-info.json`；email/name 为空时 `sub` 仍使用用户 ID，name 回退为同一 ID。让 `/authorization` 返回 401，确认 session/user-info 仍存在、`sso-access-token.txt` 不存在，侧栏显示用户 ID 和“访问令牌未就绪”。
10. 让 `/oauth2/auth` 不返回用户 ID 且 Cookie userinfo 也失败，而 `/authorization` 成功，确认 session/token 文件存在、user-info 文件不存在；反向失败时确认已经写入的 user-info 不被删除。完全关闭并重启 Desktop，确认磁盘文件只作为恢复候选，不会在上游 Cookie 校验与强制换票完成前直接显示已登录。
11. ZenMind 系统浏览器 OIDC 登录后确认 ID token 验证、基础用户信息、access token 分别落盘；模拟 Bearer userinfo 或 Site Token Bridge 失败，确认已经写入的文件不回滚。注销后确认三个 canonical 文件均删除。
12. 分别在 macOS 与 Windows 验证状态目录来自 Electron runtime/home 路径而非硬编码；macOS/Linux 使用 `stat` 确认三个文件权限为 `0600`。
13. 已有有效登录态时再次发起登录，确认等待期间仍展示原用户；让新 session 校验失败，确认原 session/user-info/token 文件和已登录状态均保留。只有新 session 校验成功后，才允许清理原账号的下游 user-info/token。
14. 让 Cookie session 返回 202，并在 `X-Auth-Request-User` 返回 `107078`，同时 userinfo 返回 200 但 `email=""`、`/authorization` 成功：确认三个文件均存在，最终用户为 `sub=107078`、`name=107078`，登录不再显示“用户信息未就绪”。再移除用户 ID 响应头并让 userinfo 不含稳定 ID，确认只保留 session/token 两个文件。
15. 让 session、userinfo、token 三步均成功，确认统一 finalize 后 WebView 自动关闭并显示真实用户；让 userinfo 成功但 token 返回 401，确认结果面板保留 session/user-info，并显示“访问令牌未就绪”。
16. 未登录时点击普通“登录”或在部分成功结果页点击“重试”，确认免登录复用；已登录账号菜单只显示“退出登录”，不显示“重新打开”或“切换账号”。
17. 注销后确认三个 canonical 文件和专用 SSO partition Cookie 全部清理，而默认 session 中无关网站 Cookie 不受影响；再次登录时确认可以选择其他账号。分别在 macOS 和 Windows 验证。登录结果为部分成功时，确认关闭、重试两个操作均可键盘访问。
18. 展开侧栏时，已登录账号在未选中 Settings 菜单路由时，确认底部触发器从左到右显示头像、用户名和最右侧齿轮；分别选中 Agents、Skills Center、MCP Connectors、Registries、Archived Chats、Market 和 Help，确认用户名改为当前路由的 i18n 名称，头像移到齿轮左侧。头像 URL 缺失或加载失败时始终显示用户名首字符，不显示路由名首字符；长文案正确截断。退出后确认改为“未登录 + 最右侧齿轮”，SSO 未配置或状态尚未加载时仍显示原“设置”入口；收起侧栏后所有状态均只显示 16px 齿轮。分别在 macOS、Windows、亮色和暗色主题下确认点击、Enter/Space 仍打开内容不变的 Settings 菜单，当前菜单路由选中态不变。
19. 先打开带稳定 `chatId` 的 Chat，再切换到 Site 或 Kanban 并从该页进入 Settings → 外观；切换中英文、手动主题和系统主题后，确认始终停留在 `/settings/appearance`，常驻但 inactive 的 Chat WebView 仍更新宿主展示参数且不反向覆盖 Desktop 路由。点击“返回应用”后应恢复进入 Settings 前的完整 pathname 与 query。分别在 macOS 和 Windows 验证。
20. 分别在 macOS 与 Windows 完成 Cookie SSO 登录，打开至少两个 Website 并确认网页已登录；完全退出 Desktop 后重新启动，确认主窗口出现前先请求 `/oauth2/auth` 和 `/authorization`，即使旧 JWT 仍有超过 15 分钟有效期也会换取新 JWT。Desktop 账户与两个 Website 必须同时恢复登录，不得出现一边已登录、另一边要求登录。
21. 检查新 JWT 写入的 `access_token` Cookie：专用 `persist:<storageNamespace>-sso` partition 和 Electron default session 中值相同，`expirationDate` 等于 JWT `exp`，且状态广播发生在两个 session 刷盘之后。用缺少合法 `exp` 的 JWT 重测，确认当前进程可用 session Cookie，但下次启动仍执行完整校验和换票。
22. 重启恢复时让 `/oauth2/auth` 或 `/authorization` 返回 401/403，确认 `sso-session.json`、`sso-user-info.json`、`sso-access-token.txt`、`secrets/sso-site-token.json` 和头像缓存被清理；专用 SSO partition 全部 Cookie 与 default session 中已知 SSO Cookie 被清理，Desktop 和 Website 同时退出。企业聊天断开，Kanban、Market 与 Tunnel Hub 不再使用旧 token。
23. 重启恢复时分别模拟断网、5 秒超时、429 和 5xx，确认 canonical 文件和上游 session Cookie 保留、两个 Electron session 中派生的旧 `access_token` Cookie 被移除；Desktop 显示“暂时无法验证登录状态”、`authenticated=false`，Website 不注入旧 JWT，企业聊天与 Tunnel Hub 不启动。重复查询状态不得从磁盘把它变回已登录。恢复网络后通过 `sso.getStatus` 或等待 5 分钟定时器，确认只发生一次并发校验/换票，所有使用 SSO partition 的 Website 各 reload 一次，Kanban、Market、企业聊天和 Tunnel Hub 恢复；Help、WebApp、agent-webclient 和普通服务 WebView 不 reload。
24. 在磁盘保留账号 A 的 user/token 后，让启动校验返回账号 B 的稳定用户 ID 并成功换票，确认账号 A 的 user/token/头像在保存 B 前清理，最终文件、侧栏、Website 和凭据消费者全部只显示账号 B，不出现字段混用。
25. 标准 OIDC 且未配置 `browserSession + cookieAccessTokenExchange` 时重启，确认仍按既有文件恢复语义处理；Help 独立 partition 和 agent-webclient Token Bridge 行为保持不变。

## 企业聊天

1. 在 `zenmind-im-server` 配置与企业 SSO access token 匹配的 OIDC issuer、audience 和 JWKS，并在 `desktop-init.json -> enterpriseIm` 显式写入布尔型 `enabled` 和服务 `baseUrl`；首次 bootstrap 后确认生成包含同值的 `config/desktop/enterprise-im.json`，服务健康检查正常。CuteJ Web 全新 runtime 应默认开启，其余正式环境与 example 默认关闭；旧 `imServer`、`im-server.json` 和 Profile 旧开关均不生效。
2. 完成 session、userinfo、access token 三步企业 SSO 登录，再到 Settings → 常规显式开启“企业聊天”，确认右下角出现 `37.8 × 37.8`（原 `54 × 54` 缩小 30%）聊天按钮，内部聊天图标仍清晰醒目；点击后打开约 `400 × 500` 的紧凑浮层，显示当前服务连接状态和除自己之外的企业员工。头像失败时显示姓名首字符；服务端返回显式 `online` 时显示在线/离线，未返回时显示灰色“在线状态未知”，不得把 `status=active` 误标为在线。联系人列表与进入私聊后的标题栏必须显示相同的 presence。联系人页必须把个人、已加入群聊和 `kind=service_bot` 机器人分区显示，并分别使用蓝色人形、绿色群组、紫色机器人图标/底色和类型标签。
3. 点击另一名员工，首次自动创建唯一 direct conversation，重复进入不创建第二个会话；发送一对一文字消息后双方实时收到，发送方消息靠右、接收方消息靠左，Enter 发送、组合键换行、空消息不可发送。
4. 关闭接收方 Desktop 后继续发送多条消息，再重新登录并连接；确认 `sync.resume` 后历史按 `seq` 恢复、消息不重复、未读徽标正确，打开会话后通过 `receipt.read` 清零。
5. 发送期间断开 `zenmind-im-server`，确认浮层显示重连状态且不丢失已确认消息；恢复服务后在最长 30 秒退避窗口内自动重连。远端 HTTP 地址应被拒绝，loopback HTTP 与远端 HTTPS 分别使用 WS/WSS。
6. 在 Settings → 常规开启“企业聊天”，确认 `enterprise-im.json -> enabled` 立即变为 `true`，在仍有完整 SSO token 时自动连接；关闭后该字段变为 `false`，按钮、浮层、内存会话和 WebSocket 立即清理，重启后保持关闭。普通 env.zip 导入必须用 `desktop-init.json -> enterpriseIm.enabled` 覆盖当前用户选择，同时用同节 `baseUrl` 热重载服务地址；`profile.json` 不得出现企业 IM 开关。
7. 注销企业 SSO，确认按钮立即消失且 WebSocket 断开；检查 renderer DevTools、URL、localStorage 和 Desktop 日志，确认不存在企业 JWT、IM session token、WebSocket ticket 或消息正文。
8. 分别在 macOS、Windows、亮色、暗色、窄窗口和矮窗口验证浮层不越界，键盘焦点、返回、刷新、关闭、员工选择和发送按钮可操作；打开右侧 Copilot 时，宽窗口下聊天浮层移到 Copilot 左侧。
9. 创建包含三名员工的私有群聊，确认会话列表、群名称、成员头像、历史、未读与群消息正常；普通成员不能越权管理成员。
10. 在私聊和群聊点击回形针，确认只打开“上传任意附件 / 打包日志与配置”菜单；前者可选择并发送任意普通文件，输入框仍可粘贴 PNG/JPEG 图片和其他文件。选择诊断包时必须先显示隐私确认；确认后收到一个 `desktop-support-*.zip`，解压检查只包含 `config/desktop`、`logs/desktop` 和 manifest，不包含服务/插件配置、secrets、SSO 状态或聊天正文，Token、Cookie、Authorization、密码、API Key、私钥、JWT、URL 凭据和本机绝对根路径均已脱敏。取消确认不得创建或上传文件。点击相机按钮时确认只弹出包含“自由截图”“当前桌面端”“整个电脑桌面”的小菜单，不会直接开始截图。依次验证自由框选、当前 ZenMind 主窗口和鼠标所在显示器全屏均可作为 PNG 发送；“当前桌面端”的截图中不得出现企业聊天 dialog 或悬浮按钮，截图完成后聊天浮层立即恢复，不等待附件上传结束。两个菜单在鼠标、Enter/Space、Esc 和亮暗主题下可用。点击消息中的图片，确认预览层覆盖整个 Desktop 内容区域而不是局限在 `400 × 500` 聊天 dialog 内，图片保持比例并可通过遮罩、关闭按钮和 Esc 退出。确认粘贴纯文本仍正常输入，附件上传期间可见忙碌状态，文件可保存到 Electron 的 downloads 路径；移出群聊后原成员不能再下载附件。
11. 拖动聊天入口到窗口四角并重启 renderer，确认位置保留且始终在可见范围内；打开面板后不越过窗口边界，拖动入口不会误触发开关。
12. 确认聊天标题栏不再显示 Desktop Action 闪电按钮，renderer、preload、IPC 和 runtime 均不存在 action 发送入口。让服务端客服机器人在一对一会话发送合法 Desktop Action，确认收到后聊天浮层内自动弹出确认框，展示请求方、摘要、动作名和脱敏参数，默认焦点在“取消”；按 Esc 或点击取消时不执行，点击确认时只执行动作目录中存在且尚未处理的动作。群聊、自己发送、重复执行、伪造 action、非法 JSON 和普通文本均不能触发执行；亮暗主题以及 macOS、Windows 下的弹框布局和键盘操作均正常。
13. 在“消息”和“联系人”页分别输入搜索词，确认两个搜索框始终位于标题栏下方且状态互不覆盖；消息按联系人姓名、邮箱、群名称和最近消息过滤，联系人按姓名和邮箱过滤。清空搜索后恢复完整列表，无匹配项时显示专用空状态；关闭再打开浮层仍保留搜索词，注销或切换账号后清空。
14. 在会话行 hover 或键盘聚焦后打开“…”菜单，取消“删除会话”确认时列表不变；确认后只在当前 Desktop 隐藏该行且未读总数不再包含它，刷新 renderer 和重启后仍隐藏。检查 localStorage 只保存按 IM Server 与当前用户隔离的 conversation ID 和 `lastSeq`，不含 token 或消息正文；其他账号的列表不受影响。
15. 隐藏私聊后从联系人再次打开，确认会话立即恢复且原历史完整；再次隐藏后由对方发送新消息，确认会话自动恢复并显示服务端未读状态。隐藏群聊后发送新群消息，确认群聊同样恢复；整个流程不得调用服务端会话删除接口。
16. 确认浮层底部显示“消息 / 联系人 / 设置”三个入口。进入设置后填写 160 字以内座右铭并选择 PNG、JPEG、WebP 头像，关闭浮层、刷新 renderer 和重启 Desktop 后均能恢复；头像超过 2 MiB、伪造扩展名或不支持格式时明确报错。切换 IM 服务地址或 SSO 账号后不得串用另一 scope 的座右铭/头像；删除自定义头像后恢复企业头像。检查 renderer 只收到 data URL，不出现本机头像路径，并明确提示这些资料只保存在当前设备、不修改企业 SSO。

## 托盘与窗口恢复

1. 分别停留在对话、项目、站点和“设置 → 智能体”页面，切换到其他应用后点击托盘图标；确认主窗口恢复并获得焦点，当前页面、详情和滚动位置均不改变。

## 退出、覆盖安装与卸载

1. 同时打开主窗口、桌宠、两个 WebApp 独立窗口和一个内嵌 WebApp 后退出；确认独立窗口和内嵌界面立即关闭，主窗口显示退出进度且阶段真实推进，最终所有 Desktop-owned PID 和监听端口归零。分别验证 macOS、Windows、亮色与暗色主题。
2. 注入忽略优雅退出的 Node、native 和 Java 子进程；确认退出进入强制清理阶段，Windows 复验完整后代 PID，macOS 依次执行 TERM/KILL，普通退出总目标不超过 8 秒。
3. 运行中执行正式覆盖安装或卸载；确认安装器等待 shutdown ack 后仍进行一次外部复验。无主实例时出现 `NO_PRIMARY` 也必须完成孤儿进程检查，不能直接删除旧版本。
4. 模拟受管进程无法终止、进程探测失败和应用 exe 文件占用；确认 Windows NSIS 与 macOS 卸载脚本中止，显示或输出残留 PID，旧应用、数据、安装记录和注册表保持可重试。
5. Windows 分别验证保留数据卸载与删除数据卸载，macOS 验证原有数据选择交互；确认只有进程复验成功后才开始删除，重复进入同一次 Windows 清理不会再次执行高成本全进程扫描。
6. 连续执行 30 次启动—退出和 10 次运行中覆盖安装。Windows 无残留时安装器进程清理目标小于 3 秒；普通退出的清理目标小于 8 秒，安装器模式小于 10 秒。
7. 全新安装后确认不创建空服务备份，三个默认核心服务健康后写入 `state/desktop/service-config-version.json`；同版本覆盖安装和普通重启不重建配置、不新增备份。
8. 分别升级和降级 Desktop `VERSION`，确认四个 `config/services/<id>` 目录严格按 Container Hub、Identity Center、Agent Platform、WebClient 各整体替换一次，且不依赖服务 manifest 版本。已有 `.desktop` 但无版本标记时确认执行一次 `legacy -> 当前版本` 重建。
9. 升级前在四个服务目录中加入旧 `.env`、YAML 和额外文件；升级后确认原目录整体进入同一事务备份，新目录只由当前服务包 deploy 生成。确认服务数据、插件、Website/WebApp、Profile 和 Secrets 均未修改。
10. 分别在 deploy 和核心 health-check 注入失败，确认新失败目录、原始目录备份和事务日志保留，版本标记不前移，Desktop 进入 degraded。再次启动确认从失败点续跑、原始备份不被覆盖，并保留上一次失败目录的临时诊断副本。
11. 连续跨三个 Desktop 版本升级，确认每次成功后只保留最近一次升级前完整目录备份。macOS 使用 `stat` 验证目录 `0700`、文件 `0600`；Windows 验证等价 ACL。分别覆盖默认数据根和 Windows 自定义 v2 DataRoot。
