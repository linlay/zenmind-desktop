# 手工测试用例

## 环境准备

```bash
npm install
npm run sync:assets
npm run dev
```

如需测试容器服务，先确认 Docker 或 Podman 可用。打包测试前先确认 `BRAND`、`ENV_ZIP`、`DEMO` 等环境变量符合目标场景；启用 Demo 时同时配置 `WEBAPP_BUILDER_SKILL_DIR`。

## 启动与核心服务

1. 启动 `npm run dev`。
2. 进入控制中心，确认 `identity-center`、`agent-platform`、`agent-webclient` 可见。
3. 首启场景下确认 `identity-center` 先 running，随后 `agent-platform` 和 `agent-webclient` 启动；服务准备期间显示全窗居中的 `StartupLoadingScreen` 卡片，包含三个核心组件的状态、已就绪数量和进度条。
4. 将核心服务启动时间延长至 45 秒以上，确认卡片显示「启动较慢」、「重新检查」和「进入控制中心」；使启动恢复失败或在恢复完成后停止任一核心服务，确认卡片显示失败信息，进入控制中心后可查看服务详情且启动卡不遮挡设置页面。分别在 macOS 与 Windows、亮暗主题和窄窗口下确认卡片可完整滚动、遮罩连续。
5. 在核心服务已就绪时停留于根路由 `/`，确认主内容区显示纯色「正在加载核心组件」兜底页；关闭最后一个 Site/Browser 并进入 `/webs` 时确认 WebView 已卸载，且主内容区显示「暂无打开的网站应用」，不再显示核心组件加载提示。随后打开 Chat、Site、设置、市场或看板，确认空状态不覆盖所选内容，标题栏拖拽区域保持正常。
6. 使用包含 `desktop-init.json`、bootstrap agent、seed JSONL、seed `chats.db`、`<bootstrapChatId>/desktop-overview.png` 和 `<bootstrapChatId>/desktop-sidebar-actions.png` 的干净 env.zip 首启，确认自动打开并选中“点击我完成初始化工作”，且从 Chats 侧栏点击该 bootstrap 会话可正常进入；仅回放 assistant 自我介绍且没有创建 run。欢迎语完全在 WebClient 原有 Chat 主区域显示，先展示标有黄色框的导航 / 内容 / 副驾或概览分区图，再展示新建 Chat、Project、Site 的侧边栏指引，图片通过既有资源接口加载。Bootstrap Chat 和 Help 均显示黄色引导框，设置菜单自动展开，并可看到完整新手引导卡与浮动气泡。
7. 在 macOS/Linux 检查导入后的任意 `.sh`（包括 `agents/bootstrap/bootstrap.sh`）权限为 `0755`，可直接以绝对路径启动；将某个已导入 `.sh` 人工改为 `0644` 后再次导入同一 env.zip，确认脚本内容仍不覆盖且权限恢复为 `0755`。Windows 对应的 `.ps1` 应使用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <absolute-path>` 启动。
8. 从初始化 Chat 主动进入 Help 或其他页面，确认本次启动不再强制跳回；重启且 bootstrap 仍存在时确认重新自动选择同一 Chat。发送消息后确认正常创建 run、接收 SSE 和处理 awaiting，profile 的正式默认 Agent 未被改写。
9. agent-platform 的 nav 列表出现 `defaultChatAgentKey` 后，确认黄色引导和引导卡立即消失、普通 Chats 列表不再显示 bootstrap 会话；当前停在 bootstrap Chat 或再次通过旧链接打开该 Chat 时，Desktop 都自动进入准确的默认智能体新会话，无需等待或接收 `run.complete`。已有 `chats.db` 时确认用户数据不被覆盖；默认智能体尚未出现时，Desktop 仍可打开 bootstrap 新会话并选中黄色降级入口。
10. 查看服务详情，确认 PID、日志路径、端口、web URL 展示正常。
11. 停止和重启 `agent-platform`，确认状态和日志更新。

## 前端嵌入与认证

1. 打开 `agent-webclient` 页面，确认 webview 正常加载。
2. 检查所有 agent-webclient URL 都不包含 `desktopAuthContext`；聊天和 Copilot 分别包含 `wsSource=desktop-chat` 和 `wsSource=desktop-copilot`。
3. 打开 Agents、Archives、Automations、Memory 和 Registries，确认 URL 不包含 `wsSource`，Network 中没有 `/ws` 连接。
4. 在 agent-webclient 中触发需要 token 的请求，确认没有手动输入 token。
5. 停止并重启 `agent-platform`，确认旧 token 被丢弃，聊天 HTTP/WS 通过 Token Bridge 恢复。
6. 打开 `identity-center` 管理页，确认进入 `/admin/`。
7. 打开 `agent-platform` monitor，确认 access token 注入后页面可访问。
8. CuteJ 登录后确认 `browserSession` 请求 `/oauth2/auth` 返回 200/202，并立即生成 `state/desktop/sso-session.json`；文件为 schema v2 且不包含 `user`、Cookie 或 access token。
9. 确认 `/oauth2/auth` 的已验证响应头包含稳定用户 ID 后立即生成 `sso-user-info.json`；email/name 为空时 `sub` 仍使用用户 ID，name 回退为同一 ID。让 `/authorization` 返回 401，确认 session/user-info 仍存在、`sso-access-token.txt` 不存在，侧栏显示用户 ID 和“访问令牌未就绪”。
10. 让 `/oauth2/auth` 不返回用户 ID 且 Cookie userinfo 也失败，而 `/authorization` 成功，确认 session/token 文件存在、user-info 文件不存在；反向失败时确认已经写入的 user-info 不被删除。完全关闭并重启 Desktop，确认状态按现存文件组合恢复。
11. ZenMind 系统浏览器 OIDC 登录后确认 ID token 验证、基础用户信息、access token 分别落盘；模拟 Bearer userinfo 或 Site Token Bridge 失败，确认已经写入的文件不回滚。注销后确认三个 canonical 文件均删除。
12. 分别在 macOS 与 Windows 验证状态目录来自 Electron runtime/home 路径而非硬编码；macOS/Linux 使用 `stat` 确认三个文件权限为 `0600`。
13. 已有有效登录态时再次发起登录，确认等待期间仍展示原用户；让新 session 校验失败，确认原 session/user-info/token 文件和已登录状态均保留。只有新 session 校验成功后，才允许清理原账号的下游 user-info/token。
14. 让 Cookie session 返回 202，并在 `X-Auth-Request-User` 返回 `107078`，同时 userinfo 返回 200 但 `email=""`、`/authorization` 成功：确认三个文件均存在，最终用户为 `sub=107078`、`name=107078`，登录不再显示“用户信息未就绪”。再移除用户 ID 响应头并让 userinfo 不含稳定 ID，确认只保留 session/token 两个文件。
15. 让 session、userinfo、token 三步均成功，确认统一 finalize 后 WebView 自动关闭并显示真实用户；让 userinfo 成功但 token 返回 401，确认结果面板保留 session/user-info，并显示“访问令牌未就绪”。
16. 未登录时点击普通“登录”或在部分成功结果页点击“重试”，确认免登录复用；已登录账号菜单只显示“退出登录”，不显示“重新打开”或“切换账号”。
17. 注销后确认三个 canonical 文件和专用 SSO partition Cookie 全部清理，而默认 session 中无关网站 Cookie 不受影响；再次登录时确认可以选择其他账号。分别在 macOS 和 Windows 验证。登录结果为部分成功时，确认关闭、重试两个操作均可键盘访问。
18. 展开侧栏时，已登录账号确认底部 Settings 菜单触发器从左到右显示头像、用户名和最右侧齿轮；头像 URL 缺失或加载失败时显示用户名首字符，长用户名正确截断。退出后确认改为“未登录 + 最右侧齿轮”，SSO 未配置或状态尚未加载时仍显示原“设置”入口；收起侧栏后所有状态均只显示 16px 齿轮。分别在 macOS、Windows、亮色和暗色主题下确认点击、Enter/Space 仍打开内容不变的 Settings 菜单，当前固定工具路由选中态不变。

## 托盘与窗口恢复

1. 分别停留在对话、项目、站点和“设置 → 智能体”页面，切换到其他应用后点击托盘图标；确认主窗口恢复并获得焦点，当前页面、详情和滚动位置均不改变。
2. 在 Windows 托盘菜单和 macOS 菜单栏中点击“打开应用”，确认只恢复当前窗口，不自动进入智能助理或设置页；点击“与应用对话”时仍正常进入对应智能助理。

## 设置：使用情况

1. 未登录但当前接口密钥有用量时，确认顶部仅显示一次“访客模式”和“使用数据按当前接口密钥统计”；统计、热力图与计费信息正常展示，且没有登录按钮。
2. 完成 SSO 登录后刷新，确认显示头像、姓名和邮箱（可用时），并仅显示一个“已登录”状态标识。
3. 登录进行中确认显示“正在登录…”，SSO 状态读取失败时显示“身份状态暂不可用”；两者均不影响当前接口密钥的用量展示。
4. 在深色主题与 720px 以下窗口宽度下，确认上下文文字可换行、刷新按钮不溢出，且头像、状态与刷新按钮可被键盘访问。

## Chats 侧栏

1. 展开 Desktop 侧栏，确认 Chats 标题默认不显示默认智能体控件；hover 标题行或通过键盘焦点进入标题行后，在折叠箭头后显示当前默认 Chat 智能体名称的紧凑选择器。点击后确认菜单顶部显示「设置对话的默认智能体」，每个选项显示「智能体名称 · 角色」，关闭态只显示名称；Enter/Space、方向键和 Escape 均可操作，说明文字不进入方向键选项。收起侧栏后打开 Chats Popover，确认同样可切换。切换中英文时菜单说明、aria 标签和更多历史文案正确。
2. 准备多个 REACT 会话并使其更新时间不同；确认 Chats 显示 agent-platform 全局排序的前 8 条，而非某个默认 agent 的 `recentChats`。准备 TEAM 或缺少 `agentKey`/有效时间字段的摘要，确认均不进入列表。
3. 产生第 9 条及更多 REACT 会话，确认 Chats 仍仅显示服务端排序的 8 条，并在末尾显示「查看更多历史」。点击后确认打开当前默认 Chat 智能体的 WebClient 历史列表；该历史可以与全局前 8 条来自不同智能体。
4. 点击任一会话，确认按该会话自己的 `agentKey` 与 `chatId` 打开；对一个未出现在导航 agent 列表中的有效 agentKey，hover 卡片应以 agentKey 作为名称兜底。点击 Chats 的「新建对话」并发送首条消息后，确认 WebClient 在取得稳定 `chatId` 时将 URL 从 `?newChat=` 替换为 `?chatId=`，新会话按服务端排序进入 Chats 后立即选中；该收敛期间协议日志只能保留原 `/api/query` live stream，不能出现随后的 `/api/chat`、`/api/attach` 或 `duplicate_observe`。仅修改 `theme`、`hostTheme`、`lang`、`wsSource` 或其参数顺序时不得重放页面；更换 `chatId`、`newChat` 时间戳或 history 参数时仍须正常导航。刷新运行中的稳定 `?chatId=` 页面时，确认仍按恢复链路请求一次 `/api/chat`，并对 active run 进行一次有效 `/api/attach`。请求失败、取消或没有稳定 `chatId` 时不得错误选中其他会话。
5. 使列表中分别存在未读、运行中和 awaiting 会话；确认对应行状态和 Chats 分组未读/等待徽标正确。未读会话在 chatName 前显示与 Projects 相同的 8px 蓝色圆点，不混入或占用标题文字；运行中显示 loading，awaiting 显示对应 Await 状态与橙色 spinner。对已展示会话依次发送带 `startedAt` / `finishedAt` 的 `run.started` / `run.finished`、带 `createdAt` / `answeredAt` 的 `awaiting.asking` / `awaiting.answered`，以及带 `createdAt` / `readAt` 的 `chat.unread` / `chat.read` push，确认状态立即更新，随后在短暂防抖后按服务端全局结果收敛；`run.started` 后等待防抖刷新，并在重启或断线重连后确认 `/api/chats` 摘要中的对象型 `activeRun` 仍让 Chats 显示 loading，run 结束且摘要不再包含 `activeRun` 后 loading 消失。以同一 `chatId` 分别位于 CODER/KBASE Projects 与 Chats 的会话覆盖 question、approval、form、planning 四种 mode，确认两处显示相同的 loading / Await，`awaiting.answered` 在 run 未结束时恢复 loading，且所有运行状态 push 都不改动 chatName 或预览文本。再发送仅含 `chatId`、`lastRunId`、`lastRunContent` 与合法 `updatedAt` 的 `chat.updated`，确认预览立即更新且主进程日志没有 `[assistant-navigation] time_contract_violation`。对非 heartbeat push 刻意发送旧 `timestamp`，确认不会更新本地状态、记录诊断并刷新快照。状态更新不依赖 push 的 `agentKey` 或该会话的 agent mode。亮/暗主题和 280–360px 侧栏宽度下均应与 Projects chat 行保持一致。
6. 打开 renderer DevTools Console，执行 `const { recentFrames } = await window.electronAPI.assistant.getNavigationLiveStatus(); console.table(recentFrames)`；确认返回 `source: "desktop-nav"`、连接阶段和脱敏 `ws://.../ws` endpoint，`recentFrames` 按时间从旧到新最多保留 20 条连接、请求、响应、push、错误或无效帧记录，且每条仅含时间、方向、事件类别和 WS type，不包含 payload、token 或 deviceId。Network 面板不显示该主进程 WS，只显示 Vite HMR 等 renderer 连接。
7. `defaultChatAgentKey` 尚未出现在 nav、bootstrap agent 可用且 bootstrap REACT 会话位于前 8 条时，确认标题显示 bootstrap 名称、引导可见且可打开该会话；默认 agent 出现后，标题和新建对话目标切换为正式默认智能体，但全局 REACT Chats 列表不按默认 agent 切换。若当时仍停在 bootstrap Chat，本次启动仅自动进入一次默认 agent 的新会话；停在 Help 或其他页面时不跳转。
8. 在 Chats 标题的 hover/focus 选择器或「助理设置」切换默认 Chat agent，确认关闭态名称、新建对话目标和更多历史目标同步更新，已返回的全局 REACT Chats 列表不被按默认 agent 过滤，当前打开的会话不跳转。保存失败时选择器恢复原值并显示错误提示。
9. 智能体加载期间或没有可用 Chat agent 时，hover/focus 后确认标题选择器保持禁用并显示不可用提示，新建对话按钮保持禁用；已有全局会话仍可按其 agentKey 打开。

## 全局搜索

1. 在展开侧边栏的顶部点击放大镜，确认与 macOS 按 `⌘K`、Windows 按 `Ctrl+K` 一样打开全局搜索；亮/暗主题下搜索面板均不显示独立的灰色底或阴影，暗色面板使用应用基础底色并保留细边框。Windows 右上角标题栏与页面遮罩颜色连续，最小化、最大化和关闭符号在搜索打开期间不可见，关闭搜索后恢复。
2. 使用键盘上下移动或鼠标移动结果行，确认仅当前结果行显示弱灰选中背景；Awaiting、Unread 状态图标容器保持透明，加载环和蓝色未读点正常显示。
3. 确认 Cmd/Ctrl+K 的 Actions 图标复用对应目标页的图标：New chat 为 Projects 中的编辑新对话图标，Agents 为机器人，Skills 为闪电，Control Center 为三条滑杆，Settings 为齿轮；Settings、Projects 和 Agents 原有图标不发生变化。
4. 在 Cmd/Ctrl+K 的「智能体」结果中，确认 `mode=CODER` 显示 coder 专用 SVG、`mode=KBASE` 显示 kbase 专用 SVG，且两者名称后不显示角色、摘要或 agentKey；普通智能体仍显示人物图标与原有次级角色/摘要文本。
5. 在 macOS 使用 `Cmd+K`、Windows 使用 `Ctrl+K`，分别验证空搜索、少量结果和大量结果：面板相对整个 Desktop 窗口（含侧边栏和 Copilot 区域）上下左右居中，宽度最多 640px、高度随内容在 240–680px 内变化；大量结果时仅结果列表滚动，搜索框与状态提示保持可见。再以窄/矮窗口和亮暗主题确认面板保留安全边距、不越界，输入焦点、Escape 和点击遮罩关闭行为正常。

## 收起态主导航视觉

1. 在亮、暗主题下展开 Desktop 侧栏，确认 Kanban 与 Automations 使用独立的 16×16 线框图标；Chats、Projects、Sites 的分组标题不显示图标。
2. 收起侧栏，确认五项改为独立的 28×28 实心 SVG，而非把 16×16 线框图标放大；点击区域仍为 56×56，选中背景使用弱灰、文字使用主文字色与 500 字重；选中图标仍使用导航主蓝色（Kanban 保留三条彩色竖轨）。
3. 确认收起态 Kanban 为三条彩色竖轨、Automations 为镂空指针的实心时钟、Chats 为带三点的实心对话气泡、Projects 为带横向留白的实心文件夹、Sites 为带单一纬线与两条细长经线镂空的简化实心地球；Sites 不出现分块式地球。
4. 确认 Chats、Projects、Sites 的收起态文案与展开态完全一致；底部工具区和收起按钮图标仍保持 16×16 紧凑尺寸，Skills 使用镂空闪电图标；主导航的 Popover、焦点漫游和路由行为不变。
5. 打开普通 Chat 智能体的会话（含 bootstrap、未读、运行中和等待中会话）时，Chats 是唯一处于选中态的分组；打开 CODER/KBASE 项目、其会话、历史或新建对话时，Projects 是唯一处于选中态的分组。展开态标题保持透明，收起态显示弱灰选中背景、主文字色与 500 字重。切换收起/展开、亮/暗主题、刷新、深链和 pending 跳转后均不得同时选中 Chats 与 Projects；未知智能体在类型数据返回前不显示这两个分组的选中背景。
6. 打开由底部 Settings 菜单进入的 Agents、Archives、Registries、Market 或 Skills 页面，确认底部 Settings 触发器显示弱灰选中背景、主文字色与 500 字重；关闭或打开菜单均不恢复蓝色选中态。

## 本地网站应用

### Manifest 与兼容

1. 分别准备 schema v4 的纯静态、Node、native、Java、external container 包，以及 `static`、`proxy` 两种 frontend；确认列表能读取，设置详情显示 version、target、launcher 和 ownership。
2. 依次构造缺少 v4 `version`/`target`/`health`、proxy 无 backend、Java 非 JAR、container 带 `entry`/`args`/`env`、非法 launcher 和非法 frontend mode，确认导入失败且不产生部分安装。
3. 构造当前 OS/架构匹配和不匹配的 `target`，分别通过本地导入与市场安装，确认不匹配资产在替换旧版之前被拒绝。
4. 对 frontend/backend 路径测试绝对路径、`..`、隐藏段、符号链接逃逸和 shell 文本，确认全部被拒绝。
5. 编辑 schema v2 WebApp 的 Copilot 设置，确认写回 v3；编辑 v3 保持 v3；编辑 v4 保持 v4、`launcher`、`jvmArgs`、container 和 frontend 联合字段，不写成 Node-only 结构。

### Gateway 与静态应用

1. 启动纯静态 v4 应用，确认只有独立 `127.0.0.1` gateway、无子进程，state 为 `running` 且 `backendUrl` 为空、`backendPort`/`pid` 为 null。
2. 验证根路径资源、localStorage、Service Worker、静态文件 MIME、SPA fallback 与 `spa=false` 的 404。
3. 在 `static` 模式验证只有 `apiPrefix` 被代理；在 `proxy` 模式验证页面和 API 整站代理。
4. 用长响应、chunked streaming、SSE 和 WebSocket 分别验证代理；停止后确认 listener、socket 和端口全部释放。
5. 请求 `/__desktop/*`，确认永不落到后端；通过 `/__desktop/actions/call` 调用允许的助理动作，确认本地同源成功而公网 Origin 返回 403。
6. 同时启动两个应用，确认端口与 origin 独立，一个应用停止或异常不影响另一个。

### Node 与原生进程

1. 清空系统 Node 路径后启动 v4 Node 包，确认仍使用 Electron runtime 的独立子进程，且安装阶段没有执行 `npm install`。
2. 后端检查 `HOST`、`PORT`、`WEBAPP_ID`、`WEBAPP_ROOT`、`WEBAPP_DATA_DIR`、`WEBAPP_STATE_DIR`、`WEBAPP_LOG_DIR`，确认值正确且目录已创建。
3. v4 托管后端检查短效 action token 可调用授权动作，runtime.json、日志和移动端 catalog 不包含 token；stop、restart、异常退出后旧 token 立即失效。v2/v3 行为保持兼容。
4. 让 Node 后端启动失败、健康超时和运行中异常退出，确认 gateway 关闭、状态为 `error`、整个进程树被清理且错误进入 `error.log`。
5. 在 macOS arm64/x64 与 Windows arm64/x64 对相应 native 资产验收；确认不在目标机安装 Go/Rust，macOS 修复执行位，Windows 拒绝非 `.exe` 入口。
6. 对 native 后端验证 HTTP/TCP 健康、日志、显式参数/环境、健康超时、停止和子进程树清理。

### Java

1. 在 Settings → WebApp Runtime 分别测试自定义 `javaExecutable`、`JAVA_HOME` 和 `PATH` 查找顺序；保存后重新检查前置条件。
2. 模拟找不到 Java、探测超时、Java 17、Java 21 和 Java 25；确认前三者显示脱敏 `blocked` 原因，21/25 可运行并显示实际路径、版本和 `java.home`。
3. 用 `javac --release 21` 构建的真实 JAR 在 macOS 与 Windows 各验收一次，确认启动形态为独立 `java [jvmArgs] -jar ... [args]` JVM。
4. 使用仅带 JRE 与完整 JDK 的环境各验收一次；确认不限制 OpenJDK 厂商、不设置最高版本，并且 Desktop 不下载或安装 Java。
5. JavaFX/JNI 包分别验证：未自带 JavaFX 时前置或启动失败清晰；JNI 只接受与当前平台匹配的资产。

## 打包与卸载

1. macOS 执行 `BRAND=zenmind npm run dist:mac`，确认 DMG 输出。
2. Windows 主机执行 `BRAND=zenmind npm run dist:win`，非 Windows 主机执行 `npm run dist:win-docker`。
3. 设置 `ENV_ZIP` 打包，确认首启导入只复制缺失文件。
4. 设置 `DEMO=true WEBAPP_BUILDER_SKILL_DIR=<webapp-builder skill 绝对路径>` 打包，确认从 skill 的 `assets/demo-node-html` 取资源并在首启安装；确认 `dist-renderer` 不包含 `webapp-templates`。
5. macOS 运行应用包内 `uninstall.sh`，确认默认保留数据，选择清理时删除运行数据和程序数据。
6. 分别运行 ZenMind/CuteJ Windows 安装器，确认界面没有程序目录选择页，实际 `$INSTDIR` 始终为 `%LOCALAPPDATA%\Programs\<ProductName>`；即使静默安装传入 `/D=<其他路径>` 也不得改变程序安装目录。在唯一的数据目录页选择父目录，确认实际 `DataRoot` 为 `<父目录>\.<brand>`、`DataRootLayoutVersion=2`。数据根和安装根都有内容匹配的 `.desktop-owner`，程序目录标记位于同级 `%APPDATA%\<ProductName>.desktop-owner`；首次启动部署服务后该同级标记仍存在。
7. 保留一个合法且非空的已登记 `DataRoot` 后再次运行交互安装器，确认数据目录选择页仍然显示，并默认选中现有数据根的父目录；直接选择已有的 `.<brand>` 数据目录时不得生成 `.<brand>\.<brand>`。静默安装不得弹出该页面。
8. 在固定程序目录的父目录 `%LOCALAPPDATA%\Programs` 放置 sibling canary，依次测试首次安装、覆盖安装、卸载和重装；确认只创建或删除 `<ProductName>` 专属目录，父目录及 sibling canary 始终保留。已有空默认程序根可以安装，已有无标记非空默认程序根必须被拒绝。
9. Windows 数据目录选择依次测试磁盘根、用户主目录、桌面、Documents、Downloads、AppData、Windows、Program Files、UNC、重解析点、空路径、大小写变化和尾部分隔符；普通父目录与尚不存在的普通父目录都可以继续且只创建 `.<brand>`，不得出现目标路径为空或误报“不属于当前品牌”；系统、网络、重解析和磁盘根路径必须被拒绝。
10. 在程序父目录、数据根父目录以及两个专属根中分别放置 canary 文件。卸载时选择“保留数据”，以及模拟 legacy 自定义 `DataRoot`、篡改注册表、标记缺失、标记错误、重解析点，确认父目录 canary 永远保留；只有带正确标记的程序专属根、v2 数据专属根和程序数据专属根可以被清理，并确认 `$INSTDIR` 本身不因卸载器当前工作目录锁定而留下空目录。
11. 准备旧默认安装位置，确认新版可以升级并补写安装标记；准备任意旧自定义 `InstallLocation`（无论是否带安装标记），确认交互安装和静默更新都在启动旧卸载器前失败，旧目录字节不变，并提示先使用 Safe Repair。
12. 对危险旧安装运行品牌化 `Safe Repair <version>.exe`，确认它要求先备份，生成 install/uninstall 注册表备份和说明文件，只移除旧安装发现注册项，不修改 `DataRoot` 或旧目录；随后新版安装成功。确认 Repair.exe 及 `.sha256` 通过校验，且 `latest.yml` 不引用 Repair.exe。
