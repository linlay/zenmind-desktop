# 插件开发

## 1. 当前实现

Desktop 插件是带 `manifest.json` 的本地 ZIP 包。导入后，程序文件安装到品牌程序数据目录的 `plugins/<plugin-id>/<version>/`；用户配置、运行状态和日志分别位于 `config/plugins/<plugin-id>/`、`state/plugins/<plugin-id>/`、`logs/plugins/<plugin-id>/`。

导入链路为：

```text
plugin.zip
  -> 校验 ZIP 与单个顶层目录
  -> 读取并规范化 manifest.json
  -> 校验 pluginApiVersion、平台、包根目录、requiredPaths
  -> 复制到 plugins/<id>/<version>/
  -> 保留已有 configFiles 与资源 ownership
  -> 注册为 plugin service
  -> resource 插件立即初始化；其他插件等待用户初始化
```

当前插件协议版本是 `pluginApiVersion: 1`。所有平台的插件导入入口只接受 `.zip`，不接受 `.tar.gz`。

## 2. 支持的插件类型

类型不是通过 `kind` 字段声明的，而是由 Manifest 能力组合推导。

### 2.1 运行时服务插件

声明 `lifecycle.start` 或 `lifecycle.stop`，或者完全没有 `resources` 时，`serviceMode` 为 `service`。服务插件需要完整的 `start` 和 `stop`，可以再声明 `deploy`、端口、健康检查、后端入口和 UI。

常见用途：本地后端、系统常驻工具、剪贴板、划词菜单、桌面浮层、网盘。

### 2.2 资源插件

只声明 `resources` 且不声明启停命令时，`serviceMode` 为 `resource`。导入后会立即初始化并同步资源。

当前资源类型：

- `resources.webapps`：复制本地 WebApp 到 Desktop WebApps 数据目录。
- `resources.agents`：向 agent-platform 创建或更新插件拥有的 Agent。
- `resources.automations`：向 agent-platform 创建或更新插件拥有的 Automation。

Desktop 通过 `plugin-resources.json` 记录 ownership，停止或卸载时只清理该插件拥有的资源。

### 2.3 混合插件

可以同时声明 `lifecycle` 与 `resources`。此时它仍是 `service`，初始化时既执行 `deploy`，也同步资源。例如 Calendar 同时包含日历后台进程与一个可交互 WebApp。

### 2.4 UI 类型

`service.ui` 支持：

- `none`：无服务页面，通常使用 Desktop action、系统 UI 或资源 WebApp。
- `embedded`：在 Desktop 内嵌打开服务 URL。
- `standalone`：作为独立服务页面打开。

插件还可通过 `desktop.actions` 暴露 Control Center 动作，通过 `hooks` / `bridge` 实现系统集成。这些是能力维度，不是新的 `kind`。

## 3. 包结构

ZIP 解压后必须只有一个顶层目录，而且目录名必须等于 `desktop.bundleTopLevelDir`；未声明时默认等于 `id`。

```text
my-plugin.zip
└── my-plugin/
    ├── manifest.json
    ├── deploy.sh | deploy.ps1
    ├── start.sh  | start.ps1
    ├── stop.sh   | stop.ps1
    ├── bin/
    │   └── my-plugin | my-plugin.exe
    ├── frontend/
    └── resources/
```

正式包应携带预编译程序。不要在用户初始化插件时依赖 Go、Swift、Node 编译器或 Xcode；`deploy` 只负责幂等地校验包、准备运行目录和生成插件自己拥有的初始配置。

## 4. Manifest 总览

最小服务插件示例：

```json
{
  "pluginApiVersion": 1,
  "id": "my-plugin",
  "name": "My Plugin",
  "version": "v1.0.0",
  "description": "插件说明",
  "platform": { "os": "darwin", "arch": "arm64" },
  "service": {
    "ui": "none"
  },
  "lifecycle": {
    "deploy": "deploy.sh",
    "start": ["start.sh", "--daemon"],
    "stop": "stop.sh"
  },
  "runtime": {
    "pidRelativePath": "run/my-plugin.pid",
    "logRelativePath": "run/my-plugin.log",
    "errorLogRelativePath": "run/my-plugin.stderr.log",
    "requiredPaths": [
      "manifest.json",
      "bin/my-plugin",
      "deploy.sh",
      "start.sh",
      "stop.sh"
    ]
  },
  "desktop": {
    "bundleTopLevelDir": "my-plugin"
  }
}
```

### 4.1 基本信息与平台

- `pluginApiVersion`：当前必须为数字 `1`。
- `id`：插件和安装目录的稳定 ID，不能包含路径分隔符。
- `name`、`description`：显示信息。
- `version`：安装版本目录名，不能包含路径分隔符。
- `platform.os`：推荐明确写 `darwin`、`windows` 或 `linux`；也接受 `any` / `universal`。
- `platform.arch`：推荐明确写 `arm64` 或 `amd64`；也接受 `any` / `universal`。

不同平台具有不同二进制或脚本时，应分别输出 ZIP，而不是在同一个包中依赖隐式回退：

```text
my-plugin-v1.0.0-darwin-arm64.zip
my-plugin-v1.0.0-windows-amd64.zip
```

### 4.2 服务与生命周期

- `service.ui`：`none | embedded | standalone`。
- `service.web.healthPath`：服务 URL 与健康检查路径。
- `service.web.portEnvKey`：端口环境变量，例如 `PORT`。
- `service.web.defaultPort`：默认端口。
- `backend.entry`：可选的后端入口说明。
- `lifecycle.start`、`stop`、`deploy`：字符串或字符串数组；数组第一个元素是脚本，后续是参数。
- `prerequisites`：依赖的 Desktop service ID 列表。

`desktop.autoStart` 当前不是协议字段，不会产生自动启动行为，不应写入 Manifest。

### 4.3 配置和运行状态

`configFiles[]` 字段：

- `key`、`label`。
- `relativePath`：相对插件配置目录的目标文件。
- `templateRelativePath`：相对插件安装目录的模板。
- `required`：缺失时是否进入 config-required。

`runtime` 字段：

- `pidRelativePath`、`logRelativePath`、`errorLogRelativePath`。
- `requiredPaths`：导入时必须存在于包内，初始化/运行时也用于健康检查。路径不能逃出插件根目录。

Desktop 向生命周期程序注入 `SERVICE_PROGRAM_DIR`、`SERVICE_CONFIG_DIR`、`SERVICE_DATA_DIR`、`SERVICE_STATE_DIR`、`SERVICE_LOG_DIR` 和 `SERVICE_ENV_PATH`；插件设置以 `DESKTOP_PLUGIN_SETTINGS_JSON` 注入。插件应把可变数据写到对应的数据、状态或日志目录，不要写入安装目录。

### 4.4 Desktop actions

`desktop.actions[]` 支持：

- `id`、`label`、`icon`。
- `placement`：当前为 `controlCenter`。
- `requiresRunning`：动作是否要求插件运行。
- `globalShortcut.settingKey`：把动作绑定到一个 `shortcut` 设置字段，由 Desktop 统一注册全局快捷键。

触发动作后，插件会收到 `plugin.actionInvoked:<action-id>` hook。全局快捷键应优先使用这套声明式能力，不要由插件重复注册。

### 4.5 hooks 与 bridge

插件桥协议版本为 1，macOS/Linux 使用 Unix socket，Windows 使用 named pipe。连接信息通过 `DESKTOP_PLUGIN_BRIDGE_PATH`、`DESKTOP_PLUGIN_BRIDGE_TOKEN`、`DESKTOP_PLUGIN_BRIDGE_VERSION`、`DESKTOP_PLUGIN_ID` 注入；首包必须发送认证 `hello`。

`hooks.subscribe` 是严格订阅列表，常用事件包括：

- `desktop.ready`、`desktop.beforeQuit`。
- `service.statusChanged:<service-id>`。
- `agentPlatform.ready`、`agentPlatform.stopped`、`agentPlatform.configChanged`。
- `assistant.activeTasksChanged`。
- `plugin.initialized`、`plugin.started`、`plugin.stopped`、`plugin.configChanged`、`plugin.settingsChanged`。
- `plugin.actionInvoked:<action-id>`。

`bridge.requests` 是插件请求白名单。当前处理的方法包括：

- 服务/Agent：`service.getStatus`、`agentPlatform.query`、`agentPlatform.upsertAcpProxy`、`agentPlatform.removeAcpProxy`。
- 桌宠/系统：`desktopPet.runBanner`、`desktopOverlay.showSystemUpdate`。
- Chat 状态：`assistantRuns.getActiveTasks`、`desktopActivityIsland.update`、`desktopActivityIsland.hide`。
- 日历：`desktopCalendarOverlay.update`、`desktopCalendarOverlay.hide`。
- 剪贴板：`desktopClipboard.readText`、`writeText`、`readContent`、`writeContent`、`showPalette`、`hidePalette`；content 方法支持文本和图片，旧的 shortcut 请求仍存在，但新插件应使用 `desktop.actions[].globalShortcut`。

即使 Desktop 实现了某方法，插件没有在自己的 `bridge.requests` 中声明也不能调用。

### 4.6 settings

`settings.schemaVersion` 当前使用 `1`。`settings.fields[]` 支持：

- `text`、`textarea`、`number`、`boolean`。
- `select`、`multiselect`，搭配 `options: [{ label, value }]`。
- `shortcut`。
- `duration`，值为数字，由插件定义毫秒或其他单位并在 label/description 中写清楚。

通用字段包括 `key`、`label`、`description`、`required`、`placeholder`、`defaultValue`、`defaultValueByPlatform`、`min`、`max`、`step`、`restartRequired`。

`defaultValueByPlatform` 的 key 是 `darwin | win32 | linux`，注意这里 Windows 使用 Electron 平台名 `win32`，而 `platform.os` 使用包平台名 `windows`。

如需完全自定义设置页，可声明 `settings.ui.customHtmlPath`。

### 4.7 resources

```json
{
  "resources": {
    "webapps": [{ "id": "calendar", "source": "webapp/calendar" }],
    "agents": [{ "key": "helper", "definition": { "name": "Helper" } }],
    "automations": [{
      "id": "daily-review",
      "name": "Daily review",
      "cron": "0 18 * * *",
      "agentKey": "helper",
      "enabled": true,
      "query": { "message": "Review today" }
    }]
  }
}
```

WebApp `source` 必须位于插件目录内。Agent 和 Automation 同步失败时会记录 pending 状态，并在 agent-platform 恢复后重试。

### 4.8 desktop 的其他能力

`desktop` 还支持：

- `assetFileName`、`bundleTopLevelDir`。
- `envBindings`：固定值、其他服务值或模板环境变量绑定。
- `hosting.runtimeConfig`、`hosting.spaRoutes`、`hosting.proxyRoutes`：Desktop 托管前端时的运行配置和代理规则。
- `capabilities.provides/requires`：内置服务依赖编排使用的能力提供与要求。

例如网盘插件使用 `{ "phase": "preStart", "capability": "auth.publicKey", "action": "copyFile", "target": "configs/local-public-key.pem" }`，在启动前通过通用 capability 获得 identity-center 公钥，而不需要专属 Desktop IPC。

这部分主要面向与 Desktop 服务栈深度集成的插件。普通插件优先使用生命周期、bridge 和 resources。

## 5. 已废弃和不支持的字段

插件 Manifest 出现以下旧字段会直接导入失败：

- `kind`：插件身份由插件导入入口确定。
- `scripts`：改用 `lifecycle`。
- `frontend`：改用 `service.ui`。
- `web`：改用 `service.web`。

未知字段通常不会进入规范化结果，因此不能把 `desktop.autoStart` 等自定义字段当作已实现能力。

## 6. 导入、初始化与升级

- 导入：校验并复制程序文件，保留同插件配置文件和资源 ownership。
- 初始化：准备目录、写默认配置、执行 `deploy`、同步 resources。
- 启动/停止/重启：执行平台生命周期命令并通过 PID/URL 验证状态。
- 升级同版本：替换程序文件，但继续保留配置与资源 ownership。
- 卸载：停止服务、移除插件拥有的 WebApp/Agent/Automation、删除对应版本目录并注销服务。

Windows 生命周期使用 `.ps1`，macOS/Linux 使用 `.sh`。需要跨平台时必须在代码和 Manifest 中显式分支并分别验证。

## 7. 当前配套插件

| 插件 | 组合类型 | 平台包 | 主要接入面 |
| --- | --- | --- | --- |
| Clipboard | service + embedded | macOS arm64 | 剪贴板 content bridge、全局 action、浮层 |
| Calendar | service + resources.webapps | macOS arm64、Windows amd64 | WebApp、三日浮层、桌宠提醒 |
| Selection Menu | service + none | macOS arm64 | Accessibility 划词监听、Agent query、记录 |
| Activity Monitor | service + none | macOS arm64、Windows amd64 | active task hooks、灵动岛/桌面小组件 |
| Alarm | service + none | macOS arm64、Windows amd64 | 规则调度、桌宠提醒、预览 action |
| Pan Webclient | service + standalone | macOS arm64、Windows amd64 | 文件服务、独立 UI、`auth.publicKey` capability |

这些插件均输出单根目录 ZIP 和预编译程序。平台特有插件不会在不兼容平台上被导入；Windows 包可在非 Windows 构建机做结构与交叉编译验证，但最终交互仍需在 Windows 真机回归。

## 8. 回归检查

至少验证：

1. ZIP 只有一个顶层目录，Manifest API、平台和 requiredPaths 正确。
2. 最终包携带预编译二进制，初始化机器不需要开发工具。
3. `deploy` 可重复执行，`start`/`stop` 正确写入和清理 PID。
4. Settings 字段能保存，并按 `restartRequired` 提示。
5. 未声明的 bridge 方法被拒绝，已声明的 hook/action 正常到达。
6. resource 与混合插件能同步并只清理自己拥有的资源。
7. macOS 与 Windows 包分别导入并验证脚本、二进制、浮层和退出清理。
