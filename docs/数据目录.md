# 数据目录

## 当前状态

Desktop 把用户运行数据和可替换程序产物分开保存。运行数据位于品牌运行根目录下的 `.desktop` 子目录，共享 Skill 固定安装到品牌运行根目录的 `skills-center/`；服务和插件程序文件位于品牌隔离的平台程序数据目录。

默认路径：

| 品牌 | macOS 运行数据 | Windows 运行数据 |
| --- | --- | --- |
| ZenMind | `~/.zenmind/.desktop/` | 新安装 `%USERPROFILE%\ZenMind Data\.zenmind\.desktop\`；legacy/fallback `%USERPROFILE%\.zenmind\.desktop\` |
| CuteJ | `~/.cutej/.desktop/` | 新安装 `%USERPROFILE%\CuteJ Data\.cutej\.desktop\`；legacy/fallback `%USERPROFILE%\.cutej\.desktop\` |

程序数据目录：

| 品牌 | macOS 程序数据 | Windows 程序数据 |
| --- | --- | --- |
| ZenMind | `~/Library/Application Support/ZenMind/` | `%APPDATA%\ZenMind\` |
| CuteJ | `~/Library/Application Support/CuteJ/` | `%APPDATA%\CuteJ\` |

## 核心流程

```text
APP_BRAND.paths
  -> user-paths.ts
  -> ensureDataRoot()
  -> config / data / state / logs / cache / secrets / profiles
  -> services and plugins program roots under appData
```

运行数据根目录结构：

```text

├── config/

│   ├── services/<service-id>/

│   ├── plugins/<plugin-id>/
│   ├── webs/

│   └── marketplace/
├── data/
│   ├── services/<service-id>/
│   ├── plugins/<plugin-id>/
│   ├── pets/<pet-id>/
│   ├── webs/websites/<website-id>/（`website.json`、可选 `favicon.<ext>`）
│   ├── webs/webapps/<webapp-id>/（当前唯一安装版本）
│   ├── webs/webapp-data/<webapp-id>/（升级保留的应用数据）
```

程序数据目录结构：

```text
<program-data-root>/
├── services/<service-id>/<version>/
└── plugins/<plugin-id>/<version>/
```

## 配置与接口

- `getDataRoot()` / `ensureDataRoot()`：解析和创建 Desktop 数据根。
- `getProgramsRoot()`：解析平台程序数据根。
- `getServicesRoot()` / `getPluginsRoot()`：服务和插件程序安装根。
- `getServiceConfigRoot()`、`getServiceDataRoot()`、`getServiceStateRoot()`、`getServiceLogsRoot()`：按 service kind 分层。
- `getDesktopWebsitesDataRoot()` / `getDesktopWebappsDataRoot()`：外部网站与本地网站应用数据目录。
- `getDesktopWebappDataRoot()`：WebApp 持久数据目录，程序升级时保留。
- `getDesktopWebappInstallStagingRoot()` / `getDesktopWebappInstallBackupRoot()`：同盘事务替换的临时目录；正常状态下为空。
- `getDesktopSsoAvatarCacheDir()`：解析 Desktop 认证头像缓存目录；renderer 不接触真实文件路径。
- `config/desktop/enterprise-chat-profile.json` 保存按 IM 服务与用户哈希隔离的本地座右铭和头像
  元数据；头像字节位于 `data/desktop/enterprise-chat-profile/<scope>/`，renderer 只接收 data URL。
- `getSecretsRoot()`：本地凭据和私钥目录。
- Settings → Debug → State 通过主进程只读快照展示 `state/desktop` 下的
  `bootstrap.json`、`env-bootstrap.json`、`pet-state.json`、`sso-session.json`
  和 `sso-access-token.txt`；renderer 不能提交文件路径或读取白名单外文件。
- `.desktop/config/desktop/help.json` 仅保存 `{ schemaVersion, url }`。Help 的网页缓存和
  Cookie 位于品牌隔离的 Help partition，不得与 SSO partition 或 token state 混用。

### Windows 安装器的数据根契约

- 安装器中的“数据目录”选择的是父目录，不是可被整体删除的数据目录。新安装始终把注册表 `HKCU\Software\<storageNamespace>\DataRoot` 写为 `<所选父目录>\.<brand>`，运行时数据仍位于其 `.desktop` 子目录。
- Desktop 通过 Windows PowerShell/.NET 注册表 API 读取 `DataRoot`，并以 UTF-8 Base64 将值传回主进程，避免中文目录名经过 `reg.exe` 本地代码页输出后被错误地按 UTF-8 解码。
- 新布局同时写入 DWORD `DataRootLayoutVersion=2`，并在有效数据根写入 `.desktop-owner`。标记内容固定为 `<appId>|<storageNamespace>|data-root|v1`，用于证明整个目录归当前品牌独占。
- 自定义父目录可以是用户主目录、桌面、Documents、Downloads 或 AppData，因为安装器只创建并删除其下的 `.<brand>` 专属子目录；父目录本身永远不进入递归删除。磁盘根、UNC 路径、Windows、Program Files 和重解析点仍被拒绝。派生的数据根必须不存在，或已经带有完全匹配的所有权标记。
- 缺少 `DataRootLayoutVersion` 的注册表记录按 legacy 处理，运行时继续读取原路径，保证旧数据可访问。历史默认根 `%USERPROFILE%\.<brand>` 可以在安装时安全认领；历史自定义根不会被自动接管或递归清理。
- Windows 卸载只有在布局版本、规范化路径和所有权标记全部匹配时才递归删除专属数据根。选择保留数据，或校验被阻止时，`DataRoot` 和布局版本注册表值继续保留，方便重装和人工恢复。

## 约束与注意事项

- 文件系统路径必须通过 `app.getPath("home")`、`app.getPath("appData")` 等 Electron API 派生。
- 服务和插件程序产物不要写入 `.desktop`，`.desktop` 只保存配置、数据、状态、日志、缓存、密钥和 profile。
- Desktop 覆盖安装或降级不会整体清空 `.desktop`。版本变化只把四个核心服务的 `config/services/<id>` 作为不透明目录整体备份并重建；Desktop 不枚举或解析目录中的 `.env`、YAML 等文件。`data/services`、用户设置、插件、Web、`secrets` 和 `profiles/electron` 均保持不变。
- `config/service-backups` 含敏感配置。macOS/Linux 的备份目录必须为 `0700`、文件为 `0600`；Windows 使用等价 ACL。升级成功后只保留最近一次成功升级前备份，失败时保留原始备份、当前失败配置和事务日志。
- `env.zip` 首启导入留档在 `data/env-initial/`，实际环境展开在品牌运行根目录。
- Desktop 不再创建 `state/desktop/env-resource-sync.json`。已有 runtime 的 `agents`、`skills-center`、
  `tools`、`teams`、`registries` 由 Agent Platform deploy 处理；其状态位于
  `<runtime>/.agent-platform/runtime-resource-state.json`，未完成事务和备份也保存在同一 Platform-owned 根下。
- Platform 对 Agent/Skill/Tool/Team 以一级资源为单位保留已存在项、增加缺失项；Registry 对发行包同路径
  强制覆盖，包外用户文件保留。上一版可证明由包管理而新版移除的资源才会删除，Desktop 不解释 Registry YAML。
- `<runtimeRoot>/owner/OWNER.md` 是助理首次初始化的唯一完成标志；Desktop 只读检查其是否为普通文件并监听创建/删除，不读取内容，也不修改 `OWNER.md` 或 `BOOTSTRAP.md`。
- Desktop 只接受 `env/skills-center/`，Skill 本地导入、命令下载和卸载也只操作 `<runtime>/skills-center/`，不再读取 Platform `.env` 覆盖路径。
- 普通启动或导入只要发现已移除的旧 Skill 目录就立即失败；旧目录与新目录同时存在也同样失败，且不会创建、移动、复制、合并或覆盖任何一侧。旧环境包含已移除目录时也会在写入前拒绝。
- 用户明确执行“还原 env.zip”时，Desktop 仍会先把整个旧 runtime 改名为时间戳备份，再从只含 `skills-center` 的新包建立全新 runtime；这不是原地迁移。
- env.zip 可携带运行根暂存目录 `desktop-init/sites/<webapp-id>/`。Desktop 首次 bootstrap 完成（或已有 bootstrap state 时 preserve）后删除该 staging；已安装内容进入 `.desktop/data/webs/`，原始 env.zip 留档不变。
- WebApp 程序仍是平铺的 `data/webs/webapps/<id>/`，没有 `versions/`、`current.json` 或长期历史版本。更新只在安装期间使用同盘 `.staging` 和 `.backup` 做原子替换；成功立即删除 backup，失败恢复旧目录。
- `webapp-data/<id>` 与程序目录分离，因此成功升级和失败回退都不会覆盖应用数据。卸载 WebApp 时程序目录与对应应用数据一起删除。
- WebApp 安装 journal 只允许引用规范的 webapps、`.staging` 和 `.backup` 根内路径；Desktop 启动恢复不会跟随被篡改的越界路径。
- `.desktop/state/desktop/bootstrap.json` 是 Sites seed 的生命周期闸门。普通导入不能通过再次放入 `desktop-init.json` 恢复用户 Sites；只有“还原 env.zip”把旧 runtime 移到时间戳备份并创建无 state 的新 runtime 后，重启才重新 seed。
- Debug State 页签会明文展示并允许复制 `sso-access-token.txt`，仅用于已解锁的本地开发者调试；该页签不提供编辑、删除或目录监听能力。
- 卸载默认保留数据；清理数据需要用户确认。macOS 保持现有清理逻辑，Windows 还必须满足上述目录所有权契约。
