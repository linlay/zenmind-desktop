# 智能助理集成

## 文档定位

本文描述 Desktop 与 Agent Platform、Agent WebClient 之间的职责分工，以及 Main Assistant、Copilot 和附件链路的主要设计。接口字段、事件清单和 UI 细节以源码与测试为准。

## 系统边界

- Agent Platform 负责 Agent、Chat、Run、流式事件与工具执行的业务事实。
- Agent WebClient 负责完整聊天页面及其交互体验。
- Desktop 负责服务发现、身份交付、窗口与 surface 编排、页面上下文，以及把平台事件映射为桌面状态。

Desktop 不复制 Agent Platform 的运行状态机，也不把 renderer 变成平台 API 客户端。主进程 bridge 是唯一的平台访问边界。

Agent Platform 同时拥有 Agent catalog 的实例级全局展示顺序。Desktop 的 Projects 只是该 catalog 中当前可导航 CODER/KBASE Agent 的有序投影：导航快照、activity 合并、Git 信息补全和 Push 更新都必须保留 Platform 顺序，Copilot-only Agent 只能追加，不能触发二次排序。Desktop 不再保存按名称或按时间的本地排序偏好。

展开侧栏中的 Project 拖拽通过受限 `assistant.reorderProjects` bridge 提交 Agent key。Main 每次保存前依次读取当前 CODER/KBASE 投影和 public `/api/agents/order` 返回的完整有效 Agent 顺序，把并发新建的 Project 追加到提交序列，只替换有效序列中的 Project 槽位，再通过同一 public order 接口保存；普通与隐藏有效 Agent 的相对槽位不由 Desktop 改写，invalid Agent 槽位则由 Platform 在写入完整 admin 序列时保护。Desktop 不再读取 `/api/admin/agents` 或调用 `/api/admin/agents/order`，renderer 也不获得管理 token、Platform URL 或通用 admin 请求能力。Platform 发布 `catalog.updated` 后，Desktop 与 Agent WebClient 的顺序通过正常导航刷新收敛。

Agent Platform 也拥有 Chats 的实例级 `recent | manual` 模式和全量手动顺序。Desktop 读取导航时并行请求 `/api/chats/order` 与带探测上限的 `/api/chats`；Platform 返回的模式覆盖 Desktop profile 中仅用于启动过渡的缓存，筛选、排序和截断都由 Platform 完成。Main 只暴露受限的模式切换与相对移动 IPC，成功 mutation 后立即重读导航快照；renderer 不持久化顺序，也不改写 Chat 时间。旧 Platform 不支持 order 接口时，Desktop 保留 recent 列表并禁用菜单和拖拽，不影响打开、新建或历史功能。

Chats 手动排序只在展开的主侧栏启用，Chat item 本身支持指针和键盘直接拖拽，不显示或预留独立把手；拖动期间原 item 留在原位变淡，另用不参与列表布局的半透明 Chat 名称浮层跟随指针，其他 item 保持原位，并在两个 item 之间显示目标插入横线。浮层挂载到页面根层，避免受 Sidebar 包含块影响产生坐标偏移。收起侧栏的浮动列表、Bootstrap 占位和历史/展开操作都不参与排序。recent 下拖动会在 UI 中乐观切换 manual 并移动，保存期间锁定后续 mutation，失败同时恢复模式与列表，成功则以 Platform 重新返回的 `/api/chats` 顺序对账。Agent WebClient 本轮不消费该展示顺序，仍可按自身既有客户端规则排列历史。

## 两类助理 Surface

完整 Agent 页面嵌入 `agent-webclient`。guest 通过固定的可信 Platform Frame Port 收发普通平台数据帧与 Run 实时帧，但不获得 App access token；显式 HTTP-only 能力由 Desktop host 注入凭据，Agent Platform 业务 WS 与 Run HTTP/SSE 入口不向 guest 开放，参见[鉴权、SSO 与 Token Bridge](鉴权SSO与TokenBridge.md)。

Main Assistant 是 Desktop 自有的轻量对话 surface：renderer 发送意图，主进程通过专用 bridge 查询 Platform，并把规范化的流式状态推送给 UI。它不复用 WebClient 页面动作面，也不依赖页面 DOM 才能完成基本对话。

Desktop 进程内只有一个全局 Realtime Broker。Broker 最多建立两条物理 WebSocket：`desktop-main` Primary 承载全部普通请求、Run、全局 Push 和反向 Desktop Action/CDP；`desktop-btw` BTW lane 只承载 BTW 请求与 BTW Run。每条 lane 内的多个 Run 都是独立 RunChannel，而不是独立连接。

## Main Assistant 主流程

```text
renderer 发起对话
  -> main 校验 agent、chat 与附件上下文
  -> 必要时上传附件
  -> Assistant adapter 进入共享 Realtime Broker
  -> Broker 建立或复用 Primary 物理连接
  -> 提交 query 并等待身份匹配的 run.start
  -> 转发业务事件与终态
  -> 更新 Desktop surface 状态
```

连接按 lane、endpoint 与不含 token/过期字段的身份 session key 管理，并支持多个 Run 交错。Primary 首次需要时建立并持续复用；BTW 在首次 Side Chat 请求时懒连接，跨 Chat 和 BTW Run 复用。两条 lane 的重连状态彼此隔离，认证身份变化则共同轮换。底层 WebSocket 打开后必须先校验 Platform WS v2 `connected`；心跳周期和静默阈值来自握手协商，任意合法入站帧都刷新所属 lane 的存活时间，heartbeat 单独记录用于诊断且不作为业务 Push。一次调用成功表示 Platform 已确认对应 Run，而不只是本地排队。已接受 Run 断线后只用最后服务端序列 attach；绝不重提 query。

Assistant、导航 Push、桌宠状态、桌宠 Run attach、可信 WebClient bridge 与 Desktop WS `ap` namespace 都是 Broker consumer。RunChannel 归 Broker 所有，最多一个上游 query/attach observer stream，本地 subscriber 共享最多 2,000 个事件或 4 MiB 的 replay；未知 id/type、旧 generation、seq 回退和重复终态只进入脱敏诊断。

只有 Primary 物理连接承载 Platform 发回的 Desktop Action/CDP request 和全局 Push。Platform 为每个 run 保存独立逻辑 target；普通可见 run 沿用 query/attach 建立的绑定，`run_query`、automation 等无绑定独立 run 在 Desktop 模式下补绑当前 `desktop-main`。BTW 连接既不成为默认 Desktop target，也不接收反向桌面请求或全局 Push；Primary 收到的 `run.finished` 可以按全局唯一 runId 收敛任一 lane 的 RunChannel。父 run 结束不影响子 run，设备重连只让后续尚未发送的动作改绑新 generation，不重放已发送动作。

Main Chat、Copilot Dock 与 Kanban Chat 是仅有的 Root Observer surface，并在一个桌面窗口内至多一个 active。一个 Root Observer 可以绑定多个 RunChannel，例如 Main Chat 的主 Run 和多个 BTW Run。Overview、Debug 只是当前 Main Chat generation 下的本地 clone：从 RunChannel replay 开始并订阅本地 fan-out，不发送 upstream attach，关闭 clone 也不发送 detach。父 Main Chat 离开、Chat/context 改变、generation 被替换或 WebContents 销毁时，Broker 立即撤销全部 clone，再对变为无 observer 的非终态 Channel 发送一次 detach；后台 Run 不被 interrupt，重新打开后按 lastSeq 恢复。

WebClient 普通新聊天没有预造 `chatId/runId`，关联 query stream 的首个合法 `chat.start` 先给出 canonical `chatId`。附件暂存则可能在 query 前预建 Chat，使 outbound query 已携带 canonical `chatId` 且该 stream 不再重复 `chat.start`；Desktop 只在服务端 `request.query` 回显同时匹配提交时记录的 `requestId + chatId + owner` 后接受该身份。两条路径都会校验 active Main Chat、surface generation、`agentKey` 与 `newChat` nonce，并立即同步外层路由和 Main Chat surface owner。Broker 仍在 `run.start` 前校验 bootstrap 事件，只有随后匹配的 canonical `run.start` 才注册 Run、解析 owner并绑定可见 surface。缺失合法 Chat 身份证据、两阶段身份冲突或宿主同步失败时均 fail closed，不从 `run.start`、`chat.created` 或当前页面反推 Chat。acceptance 前断线失败，acceptance 后重连只携带 canonical identity 和 `lastSeq` attach，绝不重发 query。

## Chat 与 Run 身份

Desktop 必须保留 Platform 返回的 `agentKey`、`chatId`、`runId` 与外部业务身份，不自行合成可冲突的 run 关系。历史对话、运行终态和消息正文以 Platform 为权威；Desktop 只保存恢复 surface 所需的最小导航信息。

Chats 与 Projects 的历史入口不再进入当前 Agent Chat 的页面内历史抽屉，也不承载 Agent WebClient `/history`。Desktop 使用原生单例 dialog，通过受限 Assistant IPC 让 Main 从 Platform 读取最小 History DTO：Chats 不预筛，Projects 仅用 `agentKey` 初始化可切换的 Owner 筛选。原生 dialog 不登记 surface、不影响 Main Chat live lease；选择具有有效 Agent 身份的记录后，AppShell 把 canonical `agentKey + chatId` 导航到 Main Chat。导出继续保存到 Desktop 选择的安全路径，归档和删除完成后同步关闭 Work Panel、刷新 Sidebar，并在当前 Chat 被移除时执行回退导航。

市场等 Desktop 原生页面需要引导用户进入一类对话时，应打开显式新对话路由并传递受控的一次性 Composer 意图，由 Agent WebClient 生成可编辑草稿。Desktop 不代替用户发送消息，也不为这类入口调用 `assistant.startRun`；只有用户在 WebClient 中发送后才产生 Chat/Run。

`chat.start` 建立普通新 query 的 Chat 身份；附件预建 Chat 使用匹配的服务端 `request.query` 回显建立同一身份。`run.start` 是 Run acceptance 的唯一边界，不能替代前述 Chat 身份证据。来源 Run 的 WorkPanel 动作只有在 Chat 路由/surface owner 同步确认且 `run.start` 身份匹配后才能执行；授权建立后与页面 observer 生命周期分离，切换 Chat 不撤销该 Run 对自己 workspace 的动作权限，后续 canonical attach 可以恢复尚未成功的授权。已有 canonical `ownerChatId` 的 Main Chat surface 不要求重复 `chat.start`，并优先于更新可能滞后的 guest `currentUrl` 判定后续 query 为续聊。

Kanban 等业务发起的运行还需遵守各自的 server-prepared identity，不能把普通 Assistant query 冒充为业务原子操作。

## 首装引导 Chat

Bootstrap Agent 是系统介绍和可选用户初始化助手，不是 Desktop 可用性的门禁。首次 Desktop 安装只消费一次主进程内存信号：优先打开仍存在的固定 seed Chat；seed 已被用户删除时打开 Bootstrap Agent 新 Chat；Bootstrap Agent 不可用时回退默认 Chat Agent。普通启动、升级和保留数据后的重装都不触发该导航。

`OWNER.md` 只保存用户明确要求创建的名字与协作偏好。它可以不存在，也可以由用户删除；Desktop 不监听它、不据此迁移 Chat，也不把资料完成状态复制成导航状态。所有常规新 Chat 入口始终解析为默认 Chat Agent。

## Copilot 与页面上下文

Copilot 把指定 Agent 与当前 Website、WebApp 或内置 surface 关联。页面上下文由 Desktop 根据活动 surface 构造，至少隔离：

- 页面身份与允许暴露的 URL 信息；
- 可用的页面控制 capability；
- 当前聊天的相对路由和恢复信息；
- 用户显式选择或上传的内容。

页面切换、关闭或来源变化时必须失效旧上下文。页面控制继续经过统一动作桥和确认策略，Copilot 身份本身不授予额外权限。

Copilot Dock 是 Desktop 当前唯一的 Copilot live surface。Dock 的实际 guest 使用固定实例身份，会话恢复则按独立的页面 `contextKey` 分区；`contextKey` 不是 surfaceId。当前上下文本身已登记为 Chat、Website、WebApp、Browser 或 Service 时，Dock 可以声明该父级，否则保持无父级，不能用 Desktop route 伪造一个 surface。Dock 的 live active 只用于自身 query、attach 与恢复，不授予公开 CDP current；父级只是页面上下文，切换、关闭、导航或刷新父页面时必须保持同一个 mounted Dock guest、WebContents 和会话。只有用户关闭应用、显式销毁 Dock guest 或 guest 自身崩溃恢复才允许重建。

Kanban route 是上述保持挂载规则的硬性例外：进入 Kanban 时 Dock 必须立即 inactive 并卸载，Launcher、System Bar 和程序化 open/toggle 都不得重新打开；Main 还会拒绝带 Kanban context 的 Dock surface 注册。离开 Kanban 后可以恢复其他页面各自保存的 Dock session，但 Kanban 自身不保存或恢复 Dock。Kanban Chat 继续作为 Primary lane Root Observer，原有 claim、run prepare、native run 与事件同步能力不受影响。

## 附件与内容

附件先由主进程校验类型、大小和来源，再上传 Platform；renderer 不持有服务密钥。上传结果与 query 使用稳定引用关联，失败时不能发送一个看似完整但缺少附件的请求。

WebApp 的图片生成与编辑复用同一条 Main Assistant、附件上传和 Realtime Broker 链路，但通过独立的最小图片桥进入。Main 固定允许的 Agent、把原图与蒙版作为严格附件上传，并要求 Agent 使用 Platform 的 `image_generate` 工具；专用流在第一次工具结果到达后立即中断 Agent，第二次 `image_generate` 启动或调用其他工具都会作为协议违规失败，因此提示词不能触发模型自行修正参数并重试。只有工具结果明确为 `ok: true`、含非空 `images[]`，且图片资源通过类型、字节上限、哈希和 Chat 归属校验后才会返回成功。工具结果中的 Chat 路径只留在 Main，页面仅得到图片内容以及 Run/Chat 标识。输入附件上传失败、工具失败、Agent 最终文字声称成功、资源缺失或资源校验失败都必须整体失败，不能降级成无原图的文生图或从最终 Markdown 猜测资源地址。

截图、页面选区和本地文件属于不同授权来源，应在 UI 和审计信息中可区分。临时文件在运行结束、取消或超时后按所有权清理。

## 对话导出与分享

Markdown 由 Agent Platform 对持久化 Chat 做一次一致读取后生成。静态 HTML 使用同一次投影得到的 `ConversationSnapshotV1`：Desktop 常驻 Worker 从 Platform 读取 Snapshot、从正在运行的 WebClient HTTP Host 读取并缓存模板，以单次分配字节算法拼接并把 ArrayBuffer 所有权转移给 main；renderer 不读取 Snapshot、模板或 HTML 字节。

创建公开分享由 Desktop main 的应用服务按固定顺序执行：先解析当前 SSO 与 Tunnel target，再把可信 Platform/WebClient 地址、短期 Platform token 和资源 origin 交给 Worker，最后把生成的有界 Buffer 作为不透明正文 POST 到 Tunnel。列表与撤销直接调用 Tunnel。Platform 只理解 Chat、Snapshot 和 Markdown，不接收 Tunnel token，也不感知模板或链接生命周期；失败时不回退旧 Platform HTML API 或 Main 拼接。完整边界见[对话快照分享与导出](对话快照分享与导出.md)。

## 状态、时间与故障

- renderer 先读取快照再订阅增量事件，重连后重新对账。
- Platform 的无效必填时间会使该事件被拒绝并触发刷新，Desktop 不用当前时间补写。
- shared contract 中的时间统一为 `EpochMilliseconds`，参见[时间契约](时间契约.md)。
- Platform 未就绪时 surface 显示可恢复状态，不回退到未认证的直连请求。
- 未知反向请求显式返回 unsupported/unknown，不能静默执行页面或系统能力。
- 日志保留 run 关联和故障阶段，但移除 token、正文与附件内容。

Debug 设置只负责打开独立的 Realtime Inspector 窗口；它不是本文所说的 Agent WebClient Debug clone，也不获得 Run observer。Inspector 可以在主窗口切换页面时保持打开，并只读展示 Primary/BTW 物理 lane、当前 Root Observer、逻辑 Frame Port、RunChannel、clone、upstream attach 状态与恢复结果。正常 heartbeat 只更新聚合状态，不逐条污染主日志。诊断数据使用进程内有界缓冲区，按可信 Surface Registry 派生的 `surfaceId` 关联，不改变 Broker 路由或页面 capability；token、Cookie、secret、用户正文和完整业务帧在跨 IPC 前递归脱敏，关闭进程后不保留。

## 扩展原则

新增助理能力应优先扩展 Platform contract 与主进程 bridge。只有涉及 Desktop 独有窗口、页面或系统能力时，才增加桌面动作；动作权限仍按[桌面协议与动作桥](桌面协议与动作桥.md)处理。

macOS 与 Windows 的文件选择、权限提示、窗口激活和系统集成必须显式分支验证。
