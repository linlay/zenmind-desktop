# 服务生命周期

## 当前状态

Desktop 用统一 service manager 管理内置服务和插件服务。生命周期覆盖安装、初始化、启动、停止、重启、状态读取、日志读取、健康检查和启动恢复。

服务定义来自 manifest，服务程序安装到品牌程序数据目录，配置、数据、状态和日志分别写入 Desktop 数据根。

## 核心流程

```text
manifest definition
  -> installBuiltinService() / installPluginFromArchive()
  -> initializeService()
  -> startService()
  -> getServiceState()
  -> stopService() / restartService()
```

安装和初始化：

- 内置服务从 bundled asset 解压或复制到 `services/<service-id>/<version>/`。
- 插件从用户选择的 `.zip` 解压到 `plugins/<plugin-id>/<version>/`。
- 非核心插件服务的缺失配置可从 manifest `configFiles.templateRelativePath` 回填。
- 内置核心服务 `agent-container-hub`、`agent-platform`、`agent-webclient`、`identity-center` 的 `.env` 和服务配置由各自 `deploy.sh` 负责创建、迁移和清理；Desktop 不做兼容修复。
- `.sh` 脚本在 macOS / Linux 上修复可执行权限。
- `scripts.deploy` 是初始化钩子，需要幂等。

Desktop 版本配置重建：

- 触发条件只看 Desktop 根 `VERSION` 字符串是否变化；服务 manifest 小版本不参与判断，降级同样触发。
- 版本变化时，Desktop 在停止服务前校验内置 env.zip 并应用新版 desktop-init 的 Desktop-owned canonical 配置；同版本不因 env.zip SHA 变化执行预检或 deploy。
- 四个核心服务按 Container Hub、Identity Center、Agent Platform、WebClient 串行执行 stop、安装当前程序包和 reset deploy。
- reset deploy 统一接收 `--desktop-config-reset`、绝对备份目录和 from/to Desktop 版本；各服务脚本原子备份自己的配置、从当前模板重建并迁移自己的凭据白名单。Desktop 不解析 `.env` 或 YAML。
- 只有 Agent Platform reset deploy 额外接收 `--runtime-resource-source`、可选的 `--runtime-resource-previous-source`、`--runtime-resource-mode version-change` 与 `--desktop-device-id`。Platform bundle 必须声明 `desktop.runtimeResources: "v1"`，并由其 Go 子命令负责 Agent、Skill、Tool、Team、Registry 的迁移；新版包声明 `provider-register.json` 时，Platform 在 Registry 强制覆盖后重新生成并注入 Provider API key。Desktop 不读写这些领域资源或注册定义。
- 部署失败或后续 running/health 失败不回滚旧配置；事务日志与失败现场留存并在后续启动续跑。原始备份只创建一次，重试前的失败配置另存临时诊断副本。
- 成功提交版本标记后只保留最近一次升级前备份。备份含敏感信息；macOS/Linux 目录权限为 `0700`、文件权限为 `0600`，Windows 使用仅当前用户和 SYSTEM 可访问的 ACL。

启动和状态：

- service manager 根据 manifest 脚本启动进程，并只追加约定的 lifecycle/layout 参数。
- `start.sh` 消费已部署配置和启动时参数；服务内部配置默认值、旧 env 清理和 runtime 目录写入必须在服务自己的 `deploy.sh` 中完成。
- Desktop 启动 `agent-platform` 时额外传入 `--identity-file <state/desktop/sso-access-token.txt>`；该参数只传路径，文件可在 Platform 启动后由登录流程创建、删除或替换，不写入服务 `.env`。
- PID、日志和错误日志路径由 manifest runtime 字段和 Desktop layout 解析。
- HTTP 服务通过端口和 web URL probe 判断 running。
- 停止时优先按 managed PID / 进程树清理，平台差异显式处理。

## Desktop 退出协调

退出不再由各模块串行拼接清理 Promise，而是由主进程统一生成 `ShutdownReport`：

1. 捕获内置服务、Desktop-owned WebApp 和受管进程树快照；关闭所有 WebApp 独立窗口，并通知 Renderer 卸载内嵌界面。
2. 并行优雅停止静态站点、WebApp、Tunnel 和服务。
3. 对失败项按快照执行平台级强制清理，最后复验捕获 PID。

普通退出目标预算为 8 秒，安装器退出为 10 秒。退出开始后主窗口切换为不可交互的真实阶段进度界面，其余窗口立即隐藏；只有报告生成后才标记清理完成并退出。Windows 的 `taskkill /T /F` 成功状态不能替代子 PID 复验，macOS 使用 `SIGTERM` 后升级到 `SIGKILL`。

安装或卸载使用 `--desktop-shutdown-for-update` 和临时目录中的品牌化 ack 文件请求主实例清理。ack 只表示 Desktop 内部协调结果；安装器仍需执行一次外部进程复验，探测失败或存在残留时必须中止。

## 配置与接口

控制中心和动作桥可触达：

- list / detail / status。
- install / initialize / start / stop / restart。
- log metadata / read log / open log viewer。

服务状态核心字段包括：

- `status`
- `healthMeta.port`
- `healthMeta.webUrl`
- `healthMeta.pid`
- `logPath`
- `errorLogPath`

## 约束与注意事项

- `agent-webclient` 可走 host-managed 模式，由 Desktop 托管静态前端和代理；本地监听端口来自 Desktop defaultPort，普通 `/api` 与 `/ws` 上游来自 host-managed start 参数 `--base-url`，不写入服务 `.env`。
- `identity-center` 认证脚本在 Windows 使用 PowerShell，在 macOS / Linux 使用 `.sh` 或后端二进制子命令。
- `agent-platform` runtime 根通过 deploy lifecycle 参数交给服务包处理；Desktop 不读取或修复 `.env` runtime 覆盖项。
- 已有 runtime 的手工 env.zip 导入同样通过 Agent Platform deploy 的 `manual-import` 模式完成领域资源迁移；空 runtime 的首装和还原仍可由 Desktop 整包展开。
- 启动失败优先检查控制中心状态、PID 文件和日志文件。
