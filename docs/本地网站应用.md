# 本地网站应用：Manifest v2

WebApp 的唯一宿主契约是 `src/shared/webapp-manifest.ts`。它定义 Manifest v2、Zod 校验与类型；`docs/contracts/webapp.schema.json` 和 `docs/contracts/webapp-manifest-validator.mjs` 均由该源码生成。`npm run webapp-contract:check` 用于检查生成物是否漂移。

Desktop 负责生成安装身份、校验 Manifest 与 ZIP、安装和升级、启动后端、托管前端、健康检查、权限控制及 Tunnel 发布。WebApp Builder Skill 负责理解需求、生成业务代码和运行项目自身构建，但必须调用 Desktop Tooling 完成最终校验和 ZIP 构建。

## 三种形态

1. **开发工程**：包含源码、测试、依赖声明、构建配置和 `webapp.json`。不得把凭据写入工程。
2. **分发 ZIP**：唯一对外传输物。只有一个 `<id>/` 顶层目录，包含运行产物，不包含 `node_modules`、缓存、日志、运行数据库或机器配置。
3. **安装与发布态**：Desktop 把程序安装到受管目录，把用户配置、SQLite、状态和日志存到包外目录。Tunnel 仅发布运行中的 gateway，不生成另一份 ZIP，也不改写程序包。

```text
webapp-35768da1bc022024.zip
└── webapp-35768da1bc022024/
    ├── webapp.json
    ├── frontend/
    └── backend/                 # 可选
```

## 完整示例

```json
{
  "schemaVersion": 2,
  "id": "webapp-35768da1bc022024",
  "key": "document-helper",
  "label": "文档助手",
  "version": "1.0.0",
  "target": "any",
  "appConfig": {
    "outputLanguage": "zh-CN",
    "promptTemplate": "按照用户设置的要求处理输入内容，只返回处理结果。"
  },
  "userConfig": {
    "fields": [
      {
        "name": "agentKey",
        "label": "智能体",
        "description": "选择执行任务的 Desktop 智能体。",
        "type": "select",
        "source": "desktop.agents",
        "default": "desktopTextGenerator",
        "required": true
      },
      {
        "name": "prompt",
        "label": "处理要求",
        "type": "textarea",
        "default": "准确处理输入内容，不添加无关说明。",
        "maxLength": 2000,
        "rows": 4
      }
    ]
  },
  "frontend": {
    "root": "frontend",
    "index": "index.html",
    "routeConfig": {
      "backendPrefixes": ["/api"],
      "navigationFallback": "index.html"
    }
  },
  "backend": {
    "command": {
      "type": "electron-node",
      "entry": "backend/server.mjs"
    },
    "args": ["--mode", "desktop"],
    "env": {
      "APP_MODE": "production"
    },
    "health": {
      "type": "http",
      "path": "/api/health",
      "startupTimeoutMs": 10000
    },
    "shutdownTimeoutMs": 3000
  },
  "desktopBridge": {
    "version": 1
  }
}
```

不需要后端或用户设置时，删除对应顶层对象。`desktopBridge` 固定为 v1，不在 Manifest 中声明 capability；省略时 Desktop 也按 v1 归一化，但新包必须显式写出该对象。

## 顶层字段

| 字段 | 作用 |
| --- | --- |
| `schemaVersion` | 固定为 `2`。未知字段和其他版本直接拒绝。 |
| `id` | Desktop Tooling 首次初始化生成的安装身份，格式为 `webapp-` 加 16 位小写十六进制。项目后续构建必须复用。 |
| `key` | 作者填写的稳定英文项目标识，3–64 位 kebab-case；本机已安装应用中必须唯一。 |
| `label` | 面向用户的名称，最多 80 个字符。 |
| `version` | 语义版本。内容变化必须提升版本。 |
| `target` | 包适用的平台和架构。 |
| `appConfig` | 随程序发布、页面只读的非敏感业务配置。 |
| `userConfig` | Desktop 设置页的字段定义和默认值；不保存实际用户值。 |
| `frontend` | 静态产物位置与有限路由规则。 |
| `backend` | 可选后端子进程、参数、环境、健康检查和停止超时。 |
| `desktopBridge` | WebApp 使用的公开 Desktop Bridge 协议版本；固定为 `{ "version": 1 }`。 |

Manifest 不包含 `openMode`、`frontend.spa`、`frontend.apiPrefix` 或 capability 下的 `instruction`、`agentKey`。打开方式属于本机用户偏好；业务提示词放 `appConfig` 或 `userConfig`。

## id 与 key

- `key` 由人填写，便于识别和评审；`id` 由 Desktop 生成，负责安装、升级和发布身份。
- ZIP 顶层目录名、Manifest `id` 和安装目标必须完全一致。
- 复制工程做成另一个产品时，应删除旧 Manifest 并重新执行初始化，不能复用旧 `id`。
- 同 `id` 的更高版本执行事务升级；同版本不同内容拒绝，低版本拒绝。
- 不支持强制覆盖或导入时临时重写 ID。

## appConfig 与 userConfig

`appConfig` 是随版本发布的只读业务配置。它可以包含固定提示词、功能开关、展示规则和默认业务选项，但不得包含 token、密码、API key 或私钥。

`userConfig.fields` 定义 Desktop 设置表单，首版支持：

- `text`、`textarea`
- `number`
- `boolean`
- 静态 `select`：声明 `options`
- Desktop Agent 选择：`type: "select"` 加 `source: "desktop.agents"`。未声明该字段或用户尚未选择时，使用 Desktop 当前配置的默认助手智能体；需要安装后直接选择特定 Agent 时，可以声明目标 Desktop 环境中有效的 `default`，用户仍可在设置页切换。通用包不得硬编码品牌 Agent Key。

用户实际值保存在 `<WEBAPP_DATA_DIR>/config/user-config.json`，不写回安装包。前端读取：

```js
const appConfig = await desktop.app.getConfig();
const userConfig = await desktop.app.getUserConfig();
```

带后端的应用从 Desktop 注入的 `WEBAPP_USER_CONFIG_PATH` 读取合并后的当前值。设置保存后，运行中的后端按统一策略重启。

## 前端与 routeConfig

Desktop gateway 始终托管 `frontend.root`，`frontend.index` 是入口。路由优先级固定为：

1. Desktop 保留的 `/__desktop/**`
2. `backendPrefixes`
3. 实际存在的静态文件
4. 接受 HTML 导航且静态文件不存在时的 `navigationFallback`
5. `404`

`navigationFallback` 是明确的 HTML 导航回退，不是 `spa` 开关。缺少的 JS、CSS、图片等静态资源不会错误回退为 HTML。`backendPrefixes` 只代理到当前 WebApp 后端，不能指向任意地址，也不能覆盖 `/__desktop/**`。

第一版不支持原始 nginx.conf、正则、任意重写脚本、自定义认证头、任意文件系统 root 或访问本机其他服务。

## target 与后端运行方式

`target` 可取：

- `any`：无平台相关可执行文件、原生扩展或动态库。
- `darwin-arm64`、`darwin-x64`、`darwin-universal`
- `win32-arm64`、`win32-x64`

Desktop 同时检查声明和包内产物。`any` 包不得携带 `.node`、`.dylib`、`.so`、`.dll`、`.pyd` 等原生文件。

后端有三种类型：

```json
{ "type": "electron-node", "entry": "backend/server.mjs" }
```

使用 Electron 自带 Node，不要求目标机另装 Node。

```json
{ "type": "executable", "entry": "backend/server" }
```

用于 Go、Rust 等自包含可执行文件；必须声明精确 target，Desktop 检查 PE/Mach-O 与平台。

```json
{
  "type": "runtime",
  "runtime": "python",
  "minimumVersion": "3.11",
  "entry": "backend/server.py"
}
```

Java 同样使用 `runtime`，入口为 JAR。安装时 Desktop 检查 Python/Java 是否存在并满足最低版本；不可用时要求用户选择本机可执行文件，机器路径只保存在 Desktop 设置中。

后端由 Electron Main 通过无 shell 的 `spawn` 创建独立操作系统子进程，不是线程。`args` 按数组逐项传入。Desktop 注入 `HOST`、`PORT`、`WEBAPP_ID`、`WEBAPP_ROOT`、`WEBAPP_DATA_DIR`、`WEBAPP_STATE_DIR`、`WEBAPP_LOG_DIR`、`WEBAPP_MANIFEST_PATH` 和 `WEBAPP_USER_CONFIG_PATH`。Manifest 不得覆盖 `HOST`、`PORT`、`WEBAPP_*` 或 `DESKTOP_*`。

## health 与运行失败

HTTP health 声明 `path + startupTimeoutMs`，TCP health 只声明 `startupTimeoutMs`。安装和升级时，Desktop 临时启动新包并验证 gateway、前端和后端；失败则终止新进程、回滚安装目录并恢复旧版本原运行状态。

正常运行中每 5 秒检查一次，连续 3 次失败后进入 `error`，关闭 gateway、撤销 token 并终止进程树。子进程提前退出同样进入 `error`。Desktop 不执行无限自动重启。

## Desktop Bridge

Manifest 只声明 Bridge 协议版本，不再逐项声明 capability：

```json
{
  "version": 1
}
```

所有本地 loopback WebApp 页面默认获得 Desktop 当前已实现的公开 Bridge 白名单。页面 token、托管后端 token 和普通 Desktop Action 仍是三个独立 scope；托管后端只获得 `assistant.chat`，Tunnel 远程页面和普通 Website 不能借用本地页面权限。Manifest 中出现 capability 字段会被严格拒绝。

Agent 默认选择由 `userConfig.fields` 中 `type: "select"`、`source: "desktop.agents"` 的字段声明；用户选择的 Agent Key 按该字段的 `name` 保存在包外用户配置中。WebApp 使用 `appConfig + userConfig + 本次输入` 组合 message；Desktop 不再追加 Manifest instruction。页面或后端调用 `assistant.chat` 时只允许传 `{ message }`。

## 持久数据与 SQLite

- 安装目录只放程序，不写运行数据。
- 业务数据库放 `WEBAPP_DATA_DIR`；状态和临时文件放 `WEBAPP_STATE_DIR`；日志放 `WEBAPP_LOG_DIR`。
- ZIP 可以携带初始化 schema 或只读 seed，但不能携带运行中的用户数据库。
- SQLite 由后端独占并通过同源 API 提供给前端，使用参数化 SQL、事务和优雅关闭。
- 升级和停止发布不会覆盖 SQLite 或用户配置。

## Desktop Tooling

在 Desktop 仓库中执行：

```bash
npm run webapp:manifest:init -- --project <project-dir> --key <project-key> --label <label> --target any
npm run webapp:manifest:validate -- --project <distribution-dir>
npm run webapp:package:validate -- --project <distribution-dir>
npm run webapp:package:build -- --project <distribution-dir> --output <new-archive.zip>
npm run webapp:package:validate -- --archive <new-archive.zip>
```

所有命令返回结构化 JSON，包括 `ok`、`stage`、`code`、路径或字段、原因和修复建议。初始化只在 Manifest 不存在时生成 ID；构建拒绝覆盖已有 ZIP。

Desktop 导入只接受 ZIP，并按以下顺序校验：压缩包安全、单顶层目录、Manifest、必需产物、target 与 runtime、临时启动和事务提交。任一阶段失败都返回诊断，且不污染正式安装目录。

## 安装、运行与发布

安装成功、运行成功和发布成功是三个不同状态：

- 导入成功：包已安装，但可以保持 `stopped`。
- 运行成功：gateway 已启动且有非空 `webUrl`。
- 发布成功：Tunnel 状态为 `published`、`active=true` 且有 HTTPS URL。

停止发布只撤销 Tunnel 路由，不停止本地 runtime，也不删除数据。发布前必须有用户明确授权。

## 模块职责

- Contract：`src/shared/webapp-manifest.ts` 与生成 Schema。
- Package Validator：Tooling 与 Installer 共用的 ZIP 安全、禁用路径、必需产物、target 与原生产物校验核心。
- Installer：调用共享包校验、执行版本策略、事务安装和回滚。
- Runtime Supervisor：launcher、gateway、health、状态、日志和进程树。
- Bridge Policy：capability、token、scope 和 Agent 调用权限。
- Settings：用户配置、打开方式、本机 runtime 绑定、运行状态和发布状态。
- Skill：业务实现和构建编排；最终调用 Desktop Tooling，不维护平行 Schema 或打包协议。
