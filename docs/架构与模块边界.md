# 架构与模块边界

## 文档定位

本文描述 ZenMind Desktop 的长期架构、信任边界和模块职责。具体函数、IPC 名称、DTO 字段、配置键和页面交互以源码及测试为准，不在设计文档中重复维护。

## 系统定位

ZenMind Desktop 是连接本地运行环境、外部服务和桌面界面的 Electron 宿主。Desktop 负责本机能力与生命周期编排，但不是内置服务业务配置、云端数据或远端协议状态的权威来源。

整体结构分为六个边界：

| 边界 | 主要职责 | 明确不负责 |
| --- | --- | --- |
| Electron main | 本地资源、进程、窗口、文件系统、凭据、协议和生命周期 | 页面展示和远端服务内部业务 |
| preload | 将经过筛选的能力和 DTO 暴露给可信 renderer | 保存业务状态或透传任意 Electron API |
| renderer | React 界面、交互状态和用户工作流 | 直接读取本地文件、持有长期凭据或管理子进程 |
| WebView / WebApp surface | 承载服务前端、网站和本地应用 | 绕过宿主 bridge 获取任意 Desktop 能力 |
| shared contracts | main、preload、renderer 之间的稳定数据边界 | 承载运行时实现和平台逻辑 |
| 外部与内置服务 | 各自业务、配置、存储和迁移 | 直接控制 Desktop 原生能力 |

## 领域边界

Desktop 主进程按职责划分为以下领域：

- **应用壳与生命周期**：装配 Electron、窗口、托盘、启动阶段、退出清理和异常恢复。
- **服务与内置资源**：发现和校验资源包，分配运行目录，调用生命周期脚本并读取健康状态；服务自身负责配置内容和领域迁移。
- **插件与市场**：管理扩展包、安装记录和资源分发。插件复用宿主提供的能力边界，不扩展 Electron 信任面。
- **Web surface 宿主**：统一管理服务前端、Website、WebApp、Help、Browser 和临时工作面板的导航、partition 与能力所有权。
- **助理与桌面能力**：连接 Agent Platform，提供 Copilot、附件、桌宠和经确认的 Desktop Action。
- **对话导出与分享**：Agent Platform 解释持久化事件并输出 Markdown 或版本化 Snapshot，WebClient 拥有并提供静态模板、导出运行时与资源，Desktop 的常驻 Worker 获取两者并生成 HTML，Tunnel 保存不透明 HTML 与链接状态；Desktop main 负责可信地址、凭据、跨平台落盘和分享编排，列表与撤销直接访问 Tunnel。
- **Agent Platform 实时域**：main 内由单一 Realtime Broker 持有物理连接、Run registry、Push 路由、回放和可见 Run 绑定；Assistant、导航、桌宠、可信 WebClient surface 与 Desktop WS `ap` namespace 只能作为其 consumer。Broker 同时接收 Platform 的 `desktop.action.call` / `desktop.cdp.call` 反向 request，直接调用现有 Action/CDP handler，并按标准 response/error 或有界 stream 分块返回；取消只停止后续回包，不重发动作。
- **Agent WebClient Platform Frame Port**：Desktop guest 通过固定的 WebSocket-like port 发送和接收 Platform `request/response/stream/push/error` 帧，普通平台数据请求与 Run 实时请求均复用唯一 Realtime Broker 物理连接，Main 只改写外层 request id。高流量 live capability 只授予当前 active 的 Main Chat、Copilot Chat 或 Kanban Chat；三者至多一个 active。preload 暴露 port 早于 renderer 完成 Surface Registry 登记时，Main 只允许可信 WebView 在有界窗口内等待登记；完整授权成功前不得创建 logical socket、取 token 或连接 Broker。Frame Port contract 与 Program bundle 原子发布，不保留旧 Realtime Bridge adapter 或混合版本降级路径。
- **企业聊天与 Kanban**：维护本机投影和同步运行时；远端正文、工作流与身份仍由 Server 权威管理。
- **跨进程契约**：集中定义 DTO、动作和协议类型，避免 main、preload 与 renderer 各自维护不同结构。

领域模块可以协作，但不能绕过对方的所有权。例如市场安装器可以调用插件或 WebApp 安装入口，不能直接修改它们的内部状态；renderer 可以请求动作，不能自行执行本地命令。

## 主要流程

启动主链路保持为阶段化编排：

```text
Electron ready
  -> 确定品牌、平台路径与 Desktop 状态
  -> 加载内置资源和已安装扩展
  -> 准备并恢复核心服务
  -> 启动 Web、助理、企业聊天、Kanban 等非核心 runtime
  -> 发布 renderer 可消费的状态
```

普通跨边界调用遵循单向入口：

```text
renderer
  -> preload 暴露的受限 API
  -> main IPC handler
  -> 对应领域模块
  -> 本地资源或外部服务
```

事件和状态更新沿相反方向投影。远端页面不得直接进入通用 IPC；Service WebView、Website、WebApp 和内部工作面板分别使用与其信任级别匹配的 bridge 和 surface policy。

## 核心设计约束

- `src/main/index.ts` 只保留运行时入口，应用装配和领域逻辑放在对应模块中。
- 新增跨进程数据先定义 shared contract，再接入 preload、IPC 和 renderer。
- token、Cookie、私钥、文件系统路径和进程控制只停留在 main；renderer 只接收完成工作流所需的最小 DTO。
- Desktop main 不读取大体积 Snapshot 或拼接 HTML，也不保存分享状态。单实例常驻 Worker 从运行中的 WebClient HTTP Host 获取并缓存小体积模板，从 Platform 获取 Snapshot，以有界字节算法生成 HTML；Platform bridge 只提供 Snapshot 请求描述，Tunnel adapter 负责有界协议转发与响应校验，controller 只组合渲染、创建、列表和撤销用例。
- Desktop 对内置服务只做生命周期编排，不解析、修复或迁移服务拥有的配置。
- Website、WebApp、Service WebView、Browser 和内部工作面板使用独立的来源、partition 与能力边界，不能因界面形态相似而共享权限。
- Web surface 身份由短实例 ID、语义角色、层级、父级和交互等级共同表达。ID 只标识独立挂载的 live guest；URL、Tab、Run、长任务、原生窗口和桌宠 consumer 不得伪装成新的 surface。
- 同一 endpoint 与身份 session 在 main 中最多存在一个 Agent Platform 物理实时连接。已被 Platform 接受的 Run 断线后只按服务端序列游标 attach，不能重发 query。
- Agent WebClient 新 Chat 的聊天身份与 Run 身份分阶段建立：普通 query 的合法 `chat.start`，或附件暂存已预建 Chat 时与 outbound `requestId + chatId + owner` 完全匹配的服务端 `request.query` 回显，先同步 Desktop 路由和 Main Chat surface owner；匹配的 `run.start` 再注册 Run。来源 Run 的 WorkPanel 动作必须等待两阶段都完成；建立后的 Run 级 grant 与当前 live observer 分离，Chat 切换只 detach observer，grant 持续到 Run 终态或身份 generation 失效。
- WorkPanel 状态只由 AppShell 的统一 command/reducer 拥有；preload、Desktop Action 和 guest bridge 都是无状态入口，不能维护平行 workspace map。
- 云端 Kanban 和企业聊天内容以 Server 为权威；Desktop 本地数据库与内存状态只是缓存、outbox 或设备侧投影。
- macOS 与 Windows 的路径、进程、脚本、权限和打包差异必须在接近实现的位置显式分支。
- 构建产物和生成文件可以重建，长期维护事实以源码、共享契约和生成源为准。
