# 版本化打包与卸载

## 文档定位

本文描述 Desktop 的版本来源、发布输入、平台产物和安全卸载原则。具体命令、环境变量、安装器脚本和签名参数以 `package.json`、构建脚本及测试为准。

## 版本与发布输入

Desktop 根版本是应用发布和配置升级的唯一版本来源。包管理文件中的版本属于同步产物，不应手工维护多份。

正式发布只消费已经准备好的输入：

- 品牌配置、图标和本地化资源。
- 当前平台的内置服务 release。
- 可选的、经过完整校验的运行环境包。
- Electron main、preload 和 renderer 构建产物。
- 平台安装器、卸载器、签名和验证配置。

Desktop 打包流程不扫描相邻服务源码，也不修复上游发布物。任何服务缺失或 contract 不匹配都应在生成安装包前失败。

沙箱 preload 必须是自包含 bundle。开发启动与打包应用虽然使用不同的 Main 输出目录，也必须消费相同的已打包 preload，不能把 TypeScript 的逐文件编译结果直接交给沙箱。渲染回归应加载实际运行目录中的构建产物，不能在测试中另行打包替代，以免掩盖开发与发布路径差异。

## 平台流水线

```text
同步版本与品牌
  -> 校验运行环境和内置资源
  -> 构建 main / preload / renderer
  -> 按目标平台 stage 应用
  -> 生成安装介质
  -> 签名、公证或平台验证
  -> 校验最终产物
```

macOS 生成签名应用与 DMG，并在需要时执行公证。Windows 生成固定程序目录的 NSIS 安装器，并校验可执行文件、卸载器和发布元数据。跨平台构建只能使用明确支持的宿主或隔离环境，不能假设 macOS 与 Windows 工具链等价。

Markdown/HTML 的系统“打开方式”声明随品牌 App 一起交付。macOS 的文档类型使用 Viewer 与 Alternate 优先级；Windows 安装器在当前用户的 OpenWithProgids 下登记品牌处理程序，保留默认关联与 UserChoice，卸载时只清理仍指向本安装目录的品牌登记。应用启动后接收文件的行为见[统一文档与 WorkPanel](统一文档与WorkPanel.md#系统文件打开)。

macOS 正式应用在启动及后续窗口激活时异步刷新系统入口，同一进程内限频。选择依据是实际 App 包中的数字发布版本，而非代码中固定的目标版本：仅在相同 bundle ID、签名满足当前应用发布身份、最低系统版本和实际 Mach-O 架构适合本机的副本中选择最高版本；同版本优先使用系统或用户 Applications 目录，再使用当前副本。先登记选中的应用与随包共享扩展，二者均成功后才定向注销其余已验证副本及已消失路径的登记，最后重新刷新选中的入口；新包缺失共享扩展或登记失败时保留原有可用入口。覆盖同一路径也强制刷新，不依赖目录修改时间；旧副本启动不会把低版本重新选为系统入口。

上述流程只管理系统登记，不删除应用、用户数据或改写默认打开方式。开发身份、其他品牌或发布者、无法验证的包保持隔离；从安装磁盘、废纸篓或 App Translocation 启动时不执行清理。清理及共享登记失败不阻塞 Shell 或内置服务。macOS 再次发现磁盘上的旧 App、用户手动打开旧版或挂载安装盘时仍可能重新登记，因此这里保证刷新时按版本收敛，不承诺旧副本长期保留时系统菜单永久唯一；彻底移除旧候选需要用户移走旧应用或卸载安装盘。

macOS 的服务签名在外层 App 签名之前完成。签名改变 builtin 文件后，由随包 Platform 命令更新最终清单；之后外层签名跳过服务文件，仅封存其最终内容。App 完成签名后必须同时复验服务签名和 builtin 清单，不能再修改已封存的资源。完整性边界见[内置资源与 Manifest](内置资源与Manifest.md)。

正式 macOS 包必须使用 Developer ID Application 发布证书，缺少证书时失败，不降级为开发证书、ad-hoc 签名或未签名产物。外层 App 在签名后及生成更新 ZIP 前独立校验 Apple 证书链、发布者、品牌 bundle 身份和 designated requirement；服务签名的开发校验开关不能跳过这项发布门禁。保留 Apple 默认的发布者与应用身份约束，不能用绑定单次构建的 cdhash 作为应用身份，以便已授权的系统隐私权限在同一发布者和品牌的版本升级间保持可识别。录屏授权后分别截取两块屏幕，以及覆盖升级后的授权与截图结果，仍需在正式签名安装包上实测。

macOS 开发 App 使用独立且持久的本地证书，以保持重新构建后的权限身份。专用钥匙串仅在签名期间临时加入用户搜索列表，成功或失败后均移除本次加入的条目；不修改系统信任设置，也不自动替换已有证书。Windows 开发启动不使用这套钥匙串流程。

## 覆盖安装与配置升级

覆盖安装替换应用程序和可重建程序资源，默认保留品牌运行根和 Desktop 用户数据。Desktop 版本变化可以触发核心服务配置 reset，但不会整体删除 `.desktop`。

服务配置升级遵循：

- 停止服务前完成新资源和输入校验。
- 把旧配置作为不透明目录备份，不由 Desktop 解释字段。
- 调用服务自己的 deploy 完成重建和必要凭据迁移。
- 核心服务验证成功后才提交新版本标记。
- 失败时保留备份、失败现场和 journal，供重试与诊断。

## 安装目录与所有权

程序目录、程序数据根和运行数据根是三个不同目标，不能相互重叠。安装器只能管理带有正确品牌、路径和所有权证据的专属目录。

Windows 的目录选择使用完整的 `.<brand>` 品牌专属数据目录，父路径可选；不得把父目录、用户主目录、磁盘根、系统目录、UNC 或重解析点传给递归删除。macOS 使用独立的平台目录和卸载逻辑，不复用 Windows 注册表与标记规则。

Windows 安装器使用带安装窗口 owner 的现代系统目录选择器，避免旧树形目录窗口在高 DPI 下超出屏幕。取消选择保留原输入，窗口打开失败允许直接填写路径；目录选择结果仍须通过品牌目录名和既有路径安全校验。高 DPI 和混合显示器上的可见性必须进行 Windows 实机回归。

## 退出协调

安装、更新和卸载前先请求正在运行的 Desktop 完成内部清理，再由安装器独立检查应用进程、受管子进程和文件锁。内部 ACK 只能说明应用侧流程结束，不能替代平台级复验。

清理失败或仍有进程存活时必须中止覆盖或删除，保留原应用与用户数据。强制结束进程也只能作用于已确认属于当前品牌、程序根或数据根的进程树。
安装器自身及其子进程必须从受管进程清理范围中排除，即使在线更新安装包暂存在数据根内；进程树兜底清理也不能连带结束安装器。

## 卸载策略

- 默认保留运行数据和用户创建内容。
- 用户明确选择清理后仍要再次验证目标目录所有权。
- 只删除当前品牌专属程序、程序数据和运行数据根，不删除用户选择的父目录。
- 标记缺失、路径异常或所有权不确定时宁可保留并提示人工处理。
- 修复工具只隔离危险的旧安装记录，不扫描或删除未知旧目录。

## 发布验证

发布前至少验证版本一致性、品牌隔离、平台资源完整性、签名/公证、安装覆盖、退出协调、数据保留和安全卸载。macOS 与 Windows 分别执行真机或等价平台回归。

WebClient 的版本标签不是内容验收依据：对 Program bundle、同步资源、打包应用及部署后的前端目录执行同一 HTML/JS/CSS 指纹核验。目录包即使内容一致，只要签名或安装门禁未通过，仍不是已验收安装包；不得跳过门禁或手工改写用户安装目录来宣称修复已生效。

- `scripts/dist-mac.mjs`、`scripts/dist-win.mjs` 与平台构建脚本
- `scripts/stage-app.mjs`、`scripts/sync-env-zip.mjs`

- `scripts/after-pack.js` 与 macOS/Windows 最终包验证器
- 打包、签名、升级、进程清理和卸载测试

## Desktop 在线更新

Windows 签名协议不再携带 keyId 或 channel，信任配置只包含品牌和真实公钥。开发/生产隔离由独立发布服务器及独立公私钥实现；公钥指纹用于日志诊断。发布服务器的版本递增规则来自本机发布策略，不由待发布清单声明。旧客户端不支持无字段清单，本次需手动安装新版基线，不实现旧客户端协议迁移。

平台范围：以下 Ed25519 配置与密钥轮换要求仅适用于 Windows。Mac 正式打包不需要这些配置，继续执行既有 Developer ID 签名、公证、ZIP 生成和 Squirrel.Mac 验签。Mac Debug 页无需额外清单签名，但不绕过原生校验。

更新源由 env 的一次性 Desktop 初始化输入下发到 Desktop canonical 配置，普通运行只读取 canonical 文件，不读取品牌发布地址或服务配置。测试与生产环境使用独立更新源和签名密钥；信任公钥在构建时嵌入 main，canonical URL、远端清单及 Debug 输入不能增加受信公钥。客户端接受合法预发布版本并按 SemVer 比较；生产源是否发布预发布版本由发布流程负责。无更新配置时禁用。用户的自动下载偏好独立保存在 Desktop state，不随 env 重置。

Updates 主进程模块是检查、下载、就绪和安装状态的唯一所有者。启动延后检查、周期检查、恢复补查和用户检查共用串行操作；网络瞬时失败采用有限退避重试，主界面首次就绪后对失败检查补查一次，成功或退出时不遗留重试。签名、协议及信任校验错误不触发网络退避重试。检查失败、网络超时和配置错误仅在关于软件展示诊断与手动重试，侧栏不显示纯检查错误，即使保留上次的版本信息。侧栏只呈现已确认更新的可下载、下载进度、安装就绪与安装恢复状态。renderer 仅通过主窗口顶层 frame 的受限 IPC 获取状态、触发动作，不接收本地包路径或具备执行能力的 URL。未登录不影响更新。

两平台都只接受 HTTPS 清单与重定向。Windows 先用内置 Ed25519 公钥验证原始清单字节，再解析 v2 协议、品牌、语义版本、平台和架构，不能降级接受 v1。macOS 保持现有 v1 清单兼容，不请求额外 .sig、不依赖 Ed25519 密钥，以 Apple 应用签名及原生更新器作为真实性校验。Windows 签名文件从最终清单 URL 所在目录获取；发布先上传不可变安装包，再切换稳定清单入口。

签名清单不包含发布序号或有效期。客户端仅对高于当前安装版本的 SemVer 提供在线安装，不做在线降级；手动重装旧版后仍可重新升级到同一目标版本。生产渠道由服务器要求发布版本严格递增，开发渠道允许同版本重新签发用于测试。明显未来的发布时间拒绝。下载使用有界流及时间限制，验证声明大小和 SHA-256 后才标记下载就绪；缓存再次使用、安装前与退出清理完成后重新校验文件与清单。已就绪的安装包不阻止后续检查新版清单。就绪表示下载校验完成，不表示平台安装已成功。

用户从设置或 About 点击升级时使用同一确认流程，说明应用退出、停止本地服务及运行对话可能中断；已识别的未保存编辑合并到同一次确认。取消保留下载就绪，确认后不等待运行任务完成，直接执行既有服务退出清理。Windows 以强制清单验签与文件校验作为应用层信任门禁，再交给现有 NSIS 执行覆盖、进程复验和重启；Authenticode 可以在发布端额外签署，但不再要求当前 EXE 和安装包拥有匹配证书。该策略不改变 Windows 自身的执行限制或未知发布者提示。macOS 保留宿主 App 签名检查，清理成功后才将已校验 ZIP 通过临时、随机路径的 loopback feed 交给 Squirrel.Mac，由原生更新器验证应用签名并替换重启。不能在后台下载完成时提前交给 Squirrel，以免普通退出触发安装。进入原生阶段后失败保留诊断，用户重新启动应用恢复服务。

应用替换与服务版本升级是两个阶段：新程序启动后仍须执行现有的 canonical 配置备份、服务 deploy 和健康验证事务，不以安装器退出或应用启动等同于服务升级完成。更新模块不承担服务配置迁移或自动数据回滚。

Windows 在线更新使用可见的 NSIS 安装进度页：`--updated` 跳过数据目录选择及完成向导，成功安装后自动发起一次应用启动；旧客户端传入 `/S` 时，新安装器也切换到可见模式。普通手动安装、普通静默安装及卸载保留原有流程，macOS 不变。Windows 首次安装、覆盖安装及卸载全程显示按阶段加权的总进度条，不显示滚动活动条，不把 NSIS 脚本位置当作完成百分比。安装按准备 0%、进程清理完成 10%、旧版本处理完成 15%、解压 15–85%、复制 85%、文件安装完成及收尾 95%、成功 100% 划分。卸载按准备 0%、进程清理完成 20%、程序文件删除及数据选项 60%、所选数据清理 65%、收尾 95%、成功 100% 划分。权重是整体阶段估算，不代表耗时或字节占比；无法准确计量的等待、复制、删除与重试保持当前值。解压由 Nsis7z 的已完成 / 总解压字节回调细化到总进度区间，只推进整体进度条，文字仅显示当前阶段，不再单独显示解压百分比；解压 100% 不表示整体安装或新应用服务初始化完成。独立的可见进度控件与 NSIS 内置脚本位置进度隔离，并保留最大已达值，失败不回退也不显示成功；只有成功收尾到整体 100%。

安装器将阶段日志写入 `%TEMP%\<storageNamespace>-update-<PID>-<tick>.log`，进度详情中显示路径。每行记录系统启动后的毫秒计数及阶段（清理、旧卸载器处理、文件安装完成、安装完成、请求启动、失败或退出）；该位置不在旧卸载器清理范围内，不记录口令。`launch-requested` 只表示发起启动，不能用它判定应用健康。首次启动的服务初始化仍由应用现有启动进度页展示。出现原生安装错误时不得绕过所有权、进程退出或签名检查。

清单契约以 `src/shared/desktop-updates.ts` 和 Updates 模块校验器为准；发布辅助脚本和两平台回归入口见 `qa/updates/README.md`。

官网更新清单由 env 的 `desktop-init.json` 配置唯一的 `updates.feedUrl`，不使用 `feedUrls` 平台映射。首次安装、版本升级和手工导入将同一入口写入 canonical `updates.json`；更新输入非法时记录局部失败并保留原更新源，不阻止其他启动配置应用。更新配置通过临时文件和原子替换写入，避免失败留下半份配置。普通启动只读取 canonical 配置。客户端检查更新时按实际操作系统设置 `platform=win32` 或 `platform=darwin` 查询参数，保留其他查询参数且不将平台参数写回配置。服务端据此内部 rewrite 到独立的 Windows 或 macOS 清单；重定向后的地址保持服务端给定值，Windows 从最终清单地址获取相邻 `.sig`。

Windows 与 macOS 使用独立更新入口，版本、清单和发布过程保持独立。Windows v2 清单配套原始字节签名，macOS 使用 v1 清单与 Apple 原生验签。发布先上传安装包，再上传不可变清单及签名，最后切换对应平台入口，防止跨请求读到不同发布的文件。清单请求 404 表示暂无更新信息；签名或安装包 404、服务器错误和非法清单仍是错误。更新说明不再作为用户填写或展示内容；发布器暂保留空 `releaseNotes` 对象，新解析器允许省略。

Debug 页提供本次运行有效的手动测试清单：Windows 用户输入原始清单文本及配套签名（Mac 继续输入 v1 清单，无需 .sig），由主进程复用正式验签、公钥范围与目标校验后加载。裸安装包参数不能进入安装路径。加载不下载、不修改官网 canonical 配置或自动下载偏好；测试期间官网检查暂停，退出测试清除选择并恢复官网检查，重启不恢复测试选择。下载、退出确认和安装复用正式流程。开发实例不能安装。下载或安装进行中禁止切换/退出测试。测试输入仅接受主窗口顶层 frame，通过既有 trusted IPC 边界处理。

签名私钥只属于发布环境，不进入客户端、更新服务器或构建归档。发布端直接读取未加密 PKCS8 私钥，不再使用私钥口令；已有加密私钥只转换存储格式，保留原密钥身份和客户端公钥信任。Windows 正式打包必须显式配置品牌公钥；配置发布输入时，平台安装器生成完成后签署并复验清单，公钥必须与本次构建嵌入值一致。密钥轮换需要旧密钥签署内置新公钥的过渡版本，旧客户端不能自动信任新密钥。自动升级尚未正式上线，本次发布直接建立首个正式基线，不维护旧 Windows v1 入口或协议过渡。上线操作与恢复步骤见 `qa/updates/README.md`。

更新包的校验就绪事实独立于最近一次操作错误。清理前的可重试拒绝保留已下载包和直接安装入口，不要求重新检查或下载；缓存失效时必须重新下载校验。清理失败或进入原生安装阶段后失败保留安装包与诊断，并要求重启恢复服务后再试。两处更新入口不得因为操作错误隐藏已有更新；重启后检查到同一发布时，重新验证缓存即可恢复就绪，无需用户再次点击下载。
