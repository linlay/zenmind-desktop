# 版本化打包与卸载

## 当前状态

Desktop 版本来自 `VERSION`，当前 package version 通过 `npm run sync:version` 同步。打包使用品牌生成的 electron-builder 配置，macOS 输出 DMG，Windows 输出 NSIS。

打包前会同步品牌、env、demo、内置服务资源和构建产物。

## 核心流程

macOS：

```text
npm run dist:mac
  -> sync version / env / demo / brand
  -> validate existing builtin assets --use-existing --os=darwin --arch=arm64
  -> icons
  -> build
  -> stage:app --os=darwin --arch=arm64
  -> electron-builder --mac --arm64
  -> optional notarize and staple DMG
```

Windows：

```text
npm run dist:win
  -> Windows host: buildOnWindowsHost()
  -> non-Windows or --docker: buildWithDocker()
  -> sync builtin assets --os=windows --arch=amd64
  -> build
  -> stage:app --os=win32 --arch=x64
  -> electron-builder --win --x64
  -> build-safe-repair
  -> verify-win-package
```

## 配置与接口

常用命令：

```bash
npm run build
npm run dist:mac
npm run dist:win
npm run dist:win-docker
make release
make release-mac
make release-win
make release-win-docker
```

打包资源：

- `build/resources/services` -> `resources/services`
- `build/brands/<brand>/resources/env` -> `resources/env`
- `build/brands/<brand>/resources/demo` -> `resources/demo`
- brand icon / mark / tray icon
- macOS `uninstall.sh`
- Windows NSIS include

关键环境变量：

- `BRAND`
- `ENV_ZIP`
- `DEMO`
- `WEBAPP_BUILDER_SKILL_DIR`：仅在 `DEMO=true` 时必填，指向提供 `assets/demo-node-html` 的 `webapp-builder` skill。
- `SKIP_NOTARIZE`
- Apple notarization env：`APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID` 或 API key 组合。
- signing env：`CSC_NAME`、`MACOS_CODESIGN_IDENTITY`、`DESKTOP_DARWIN_CODESIGN_IDENTITY`。

## 约束与注意事项

- `ENV_ZIP` 必须是单顶层 `env/` 目录，不能嵌套 `.zenmind/`、`zenmind-env/` 或裸顶层文件。
- `DEMO` 只接受 `1/true/yes/on` 和 `0/false/no/off`。
- Demo 模板源码归 `webapp-builder` skill；Desktop 打包不再从 Renderer `public/` 读取模板。Windows Docker 打包会把显式配置的 skill 目录只读挂载到容器。
- Desktop 发布打包只消费当前 `build/resources/services`，不会扫描周边服务项目。macOS/Linux 的 `build-all-dist.sh` 与 Windows AMD64 的 `build-all-dist.ps1` 都只触发四个上游服务的 `make release ARCH=<arch>` 并同步其 `dist/release` 产物；服务版本、目标矩阵和私有发布依赖均由上游服务负责。macOS 刷新使用 `scripts/build-all-dist.sh --sync-os darwin --sync-arch arm64`；Windows 先运行 Platform 的 `scripts/sync-local-builtins.ps1 -Target windows/amd64`，再运行 Desktop 的 `scripts/build-all-dist.ps1 -SyncOS windows -SyncArch amd64`。
- Windows AMD64 真机完整回归使用 `powershell -ExecutionPolicy Bypass -File scripts/test-windows-release-chain.ps1`。它执行上述两阶段链路，校验四个单顶层 ZIP、Platform SHA/sizes/SBOM、Desktop 四服务 manifest，并保证运行前后 canonical `builtins.lock.json` SHA-256 不变。
- macOS 正式包在 `afterPack`、代码签名前将 `icon.icns` 改为 `icon-<sha256前12位>.icns`，并同步更新 `CFBundleIconFile`。图标内容变化时文件名随之变化，避免升级后 Finder、Dock 或系统权限列表继续命中旧尺寸图标缓存。
- Windows 非 Windows 主机打包走 Docker，避免生成损坏 NSIS 卸载器。
- macOS 卸载脚本会检查应用是否仍在运行，并询问是否删除运行数据和程序数据。
- Windows 程序安装目录固定为 `%LOCALAPPDATA%\Programs\<ProductName>`，安装器不提供程序目录选择页，并在初始化时覆盖 `/D` 等自定义目录输入。唯一可选的是数据父目录，最终数据根固定为 `<数据父目录>\.<brand>`，绝不把用户选择的父目录直接交给递归删除逻辑。程序根必须以准确的 `<ProductName>` 作为末级目录，且不得与程序数据根或运行数据根重合；已有非空默认程序根只有带匹配 `install-root` 标记或属于可迁移的旧默认安装时才可复用。
- Windows 交互安装始终显示数据位置选择页；已有合法 `DataRoot` 时以其父目录作为默认值，但不得自动跳过页面。用户既可选择父目录，也可直接选择已有的 `.<brand>` 数据目录，后者不得再次拼接成 `.<brand>\.<brand>`。只有静默安装/自动更新可以沿用已登记的数据目录而不显示页面。
- NSIS 不得在用户选择的父目录或最终 `.<brand>` 目录尚不存在时直接用 `GetFullPathName` 覆盖原变量；先拦截明显危险的原始路径，再创建目录，随后才允许规范化并重复执行系统目录、重解析点和所有权校验。否则不存在的目标会被清空并误报为“不属于当前品牌”。
- NSIS 初始化可能提前创建空的 `$INSTDIR`；安装器必须枚举目录实际条目并允许空专属目录，不能把“目录存在”误判成“含有未归属文件”。相同规则用于恢复已删除后残留的空 v2 数据根；只要发现任意真实条目，仍必须通过所有权标记校验。
- 新装时在固定 `$INSTDIR`、v2 数据根分别写入 `install-root`、`data-root` 类型的 `.desktop-owner`，并把程序目录的 `program-root` 标记写在不会被首次服务部署重建的同级文件 `%APPDATA%\<ProductName>.desktop-owner`。安装器在启动旧卸载器和释放应用文件前都校验程序根；卸载器进入 electron-builder 默认删除区段前对 `$INSTDIR` 执行路径、末级目录和所有权校验。
- Windows 卸载询问是否清理数据，但只递归删除带匹配所有权标记、通过路径规范化检查且不是重解析点的专属目录；不得对注册表读取或用户直接选择的裸目录执行递归删除。卸载器拒绝 electron-builder 的 `--delete-app-data` 旁路，且重新开启 `deleteAppDataOnUninstall` 会在 NSIS 编译期失败。清理前必须等待受管进程实际退出；NSIS 删除失败时通过环境变量把已校验路径交给 PowerShell 原生递归删除，并限时重试、恢复所有权标记，避免形成无法安全重试的半删除目录。只有实际删除成功后才清理 `DataRoot`、`DataRootLayoutVersion` 等注册表值。
- 卸载器初始化后必须先把当前工作目录切换到 `$TEMP`，再进入 electron-builder 的程序文件删除区段；否则 Windows 会因卸载进程仍以 `$INSTDIR` 为当前目录而留下无法删除的空程序根。
- Windows 安装器发现 v2 `DataRoot` 注册值仍在但目标目录已经不存在时，应把它视为上次删除完成后的可恢复状态，重新显示数据目录选择页并保留原父目录作为默认值。固定程序数据目录存在但缺少所有权标记时不得直接接管；应先原子重命名到同级 recovery 目录，再创建新的品牌专属目录。
- Windows 安装器兼容旧版本写入的 `LayoutVersion=2`，并在成功安装时迁移为 `DataRootLayoutVersion=2`；旧字段不得让已删除的数据目录被误判为不可恢复的历史目录。
- 新安装器在调用旧卸载器前读取旧 `InstallLocation`。默认安装目录可以升级；任何非默认目录记录都一律中止，包括带标记目录和静默更新，避免旧卸载器递归删除非默认目录，并保证新版程序路径始终固定。
- Windows 发布目录同时生成 `<ProductName> Safe Repair <version>.exe` 和对应 `.sha256`。Repair.exe 要求用户确认已备份，将旧安装和卸载注册项导出到 `%LOCALAPPDATA%\<ProductName>\repair-backups`，备份全部成功后才移除 electron-builder 用于发现旧安装的注册项。它不运行旧卸载器，不删除、移动或递归扫描旧目录，也不修改 `DataRoot`。
- Repair.exe 只用于隔离危险的旧版自定义安装记录，不写入 `latest.yml`，因此不会成为自动更新目标。隔离完成后重新运行新版安装器，旧目录由用户确认备份后人工处理。
- 受影响的旧 Windows 安装包不得继续分发。使用过自定义安装目录或数据目录的用户不得直接运行旧卸载器，应先使用对应品牌和版本的 Safe Repair.exe。
- macOS 安装和卸载逻辑不受上述 Windows 所有权契约影响。
