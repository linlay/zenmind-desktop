# 看板与云同步

## 文档定位

本文描述 Desktop Kanban 的数据权威、同步架构和运行边界。WebSocket envelope、DTO 字段、数据库 schema、动作参数和 UI 细节以源码、共享契约及 golden fixture 为准，不在设计文档中重复维护。

## 系统定位

Desktop 同时承载本地看板和云端 Kanban 投影，但两者具有不同的数据权威：

| 数据 | 权威来源 | Desktop 能力 |
| --- | --- | --- |
| Local Issue | Desktop 本地数据库 | 创建、编辑、移动、删除和自动化 |
| Cloud Issue 正文与工作流 | Kanban Server | 缓存和展示，不提供通用 CRUD |
| Cloud Worker、Chat、Run、Review | Kanban Server | 接收投影并执行受限设备侧操作 |
| 本机 Chat 与 Agent 运行 | Agent Platform / Desktop | 根据 Server 准备的身份启动并回报事件 |
| 同步 cursor、outbox、receipt | Desktop 本地数据库 | 断线恢复、重试和幂等保护 |

项目选择统一读取本地数据库返回的项目目录，来源由项目记录的本地／云端属性明确表达，不根据是否为默认项目推断。本地空项目也必须出现在筛选和新建问题选择中；本地项目平铺，云端项目保留目录树。

问题表单不提供独立的云同步开关，项目归属决定创建意图：本地项目只写本地，云端项目不得静默落为本地任务。当前只读合同仍拒绝 Desktop 创建云端问题；项目选择不扩大云端写权限。

Desktop 不是 Cloud Issue 的离线编辑器。网络断开时可以继续展示最近一次可信缓存，但不能把本地修改伪装成云端成功。

本地看板启用与云端连接独立：初始化允许启用看板、云地址留空且关闭远程控制；启用云端远程控制时必须提供有效的服务地址。

本地 Issue 的归属由本地来源确定，人员筛选始终归入“自己”，不依赖云端登录或补写云端负责人 ID。卡片只展示执行者，不重复展示本地归属；智能体执行展示智能体，明确为人工执行时展示“自己”。云端 Issue 继续按 Server 下发的负责人区分自己、他人与未分配。

公共 Desktop Action 读取单个 Issue 或创建、更新、移动 Local Issue 时只返回目标 `issue`，删除只返回 `deletedIssueId`；这些响应不携带看板全集或成功提示。完整 Issue 快照只由显式列表读取动作返回，领域业务失败转换为公共错误且不得在 details 中泄露 `issues` 集合。

## 本地任务公共调度

本地任务的自动执行由 Main Kanban runtime 统一拥有，与页面是否打开、任务来自普通 Chat、Desktop Action 或表单无关。启动恢复、任务变化和 Agent 运行结束后重新检查资格，并以周期检查补偿服务恢复、执行者配置变化和遗漏通知。renderer 只提交任务意图、展示状态，不持有启动定时器，也不直接启动本地 Kanban Run。

处于待办、具有 Agent 执行者、没有活动运行且未启用定时自动化的任务进入调度。未指定执行者、人工执行、Backlog、审核和终态任务不执行；阶段前进或回退到待办后同样重新判断。执行失败或用户取消的运行保留诊断状态，显式重新置为待办后才能重试，避免无限执行失败任务。

同一 Agent 的启动请求串行准入，不限制已准入 Run 的并行执行；不同 Agent 独立调度。实际运行容量由 Agent Platform 决定，不在 Desktop 复制一套只统计看板的并发计数。当前 Platform 未公开通用的每 Agent 并发配置或容量查询接口；准入被拒时任务留在待办并保留错误原因，延迟重试或由任意 Chat 的运行结束唤醒，避免普通 Chat 释放名额后队列停滞。

提交 query 前先持久化唯一 Run/Chat 身份，收到准入成功或可信运行开始事件后才进入执行中。迟到准入响应不得覆盖已经结束或推进到下一阶段的任务；不确定请求是否被接受时保留身份等待运行状态收敛，不盲目重发 query。调度随 runtime 停止而停止，macOS 和 Windows 使用相同的主进程调度与既有品牌数据目录。

待办任务首次满足执行资格后，Main 保留至少 2 秒的待办展示窗口，再申请运行；新建、补充分配执行者和阶段返回待办共用该规则。重复唤醒不得缩短窗口或重复启动，等待期间重新校验任务资格；取消分配、移出待办或停止 runtime 后不得沿用旧定时请求启动任务。

## 本地阶段工作流

本地工作流定义由当前 Desktop 数据库持有，与云端工作流目录和同步缓存分开保存。用户从看板设置菜单创建、修改阶段顺序、名称和审核要求；新建本地任务时可选择流程，也可继续使用无阶段任务。

每个本地任务持有创建时的流程快照。模板编辑或删除只影响后续创建，不能重置已有任务的阶段，也不能修改云端工作流。默认开发流程包含开发、测试和提交三个阶段；缺陷流程在开发前增加提出缺陷阶段。审核是阶段内部的状态，不单独算一个阶段。

固定看板列继续表示当前阶段的状态。完成需要审核的阶段先进入审核，人工通过后才进入下一阶段待办；同阶段退回时留在当前阶段重新处理；跨阶段回退必须沿任务流程快照中显式配置的回退路径返回前面的阶段待办，并重新经过后续执行和审核。回退必须填写原因，连同来源、目标、操作人和时间保存到本地任务记录；执行中的任务禁止回退，迟到请求不能作用于已经变化的阶段或状态。只有最后阶段结束才进入已完成列。Agent 执行结束不能替代人工审核。阶段切换清除当前运行和会话引用，下一阶段独立启动；原有自动化配置继续遵循本地任务的自动化规则。

模板修改仍不自动作用于已有任务。对于阶段标识和顺序完全一致的模板，用户可在任务详情中显式应用最新回退规则；该动作仅替换回退路径，不改变当前阶段、名称或审核要求。

本地流程读写复用现有数据库路径和 IPC 边界，macOS 与 Windows 使用相同的逻辑结构，不引入平台专属路径或云端请求。

## 同步架构

本地 Issue 的运行结果是该 Issue 最近一次运行的持久快照。Desktop 复用 Primary Realtime Broker 的导航 Push 订阅，将 `chat.updated` 的结果按精确 Run 与 Chat 身份关联并保存，再通知看板刷新；详情页直接读取本地快照，不依赖打开会话或再次查询会话摘要。`run.finished` 只结束活动运行，最近一次运行的关联独立保留，两个事件的先后顺序不能决定结果是否丢失。启动新运行时替换关联并清空旧结果，迟到或重复事件不得污染新运行；阶段自动前进保留最近一次结果的关联，但不能把旧 Chat 复用为下一阶段的活动 Chat。显式跨阶段回退清除这份运行快照。此处理只适用于 Local Issue，Cloud Issue 仍由 Server 提供权威运行记录。

```text
Kanban Server
  -> snapshot / issue event / command delivery
  -> Desktop WebSocket client
  -> Kanban runtime
  -> 本地缓存、cursor、receipt 与 outbox
  -> renderer 只读投影

本机 Agent 运行
  -> Agent Platform
  -> Desktop 运行状态映射
  -> 可靠 run event outbox
  -> Kanban Server
```

首次连接先完成合同校验和同步握手，再应用快照与增量事件。完整快照负责收敛 Server 已删除或停用的数据，增量事件只更新明确携带的实体。连接未完成前保留离线缓存，不用空结果覆盖已有数据。

缓存按当前认证用户隔离。切换账号、项目范围或 Server 时不能复用另一身份的详情、cursor、receipt 或待发送事件。

R0 已移除旧 `kanban-cloud-sync`、旧 DB/store 和通用上传同步链，以及只服务于该链的 sync result DTO。当前实现只保留 `kanban-local-store`、云端只读缓存、`resyncFromCloud`、受限原子协议与仍在使用的自动化/Run 纯函数。清理不迁移、不改写也不删除用户磁盘上的旧 Kanban 数据文件，当前新库一次性创建完整 schema；后续若需要处理残留文件，必须另立有恢复策略的数据迁移。

## 云端操作边界

当前 Desktop 只调用 Contract 1.0 允许的原子操作：

- `issue.claim`：认领符合条件的 Cloud Issue。
- `issue.run.prepare`：由 Server 预先创建运行身份并决定 Chat policy。
- `issue.chat.bind/unbind`：为 Human Run 关联或解除本机 Chat 引用。
- `run.event.append`：同步设备侧运行事件。

这些操作不是 Cloud Issue 公共 CRUD。Desktop 不直接迁移工作流、改写正文、设置标签或依赖，也不调用 Website 的运行请求入口。当前合同没有旧版本协商、字段别名或双读兼容。

## Worker、Chat、Run 与 Review

- Worker 绑定 Issue 的具体 Stage 和角色；Agent Worker 还绑定 Agent 与 Desktop 设备，不跨 Stage 隐式复用。
- 普通 Agent Run 只在 Stage、Status、Agent 和设备均一致时允许复用首选 Chat；Chat 变化不等于复用 Run。
- 每次 Agent 执行都创建新的 Issue Run 身份。Server 以 `issueRunId + deviceId + externalRunId` 精确关联事件，`chatId` 不能单独定位一次运行。
- 其他 Desktop 的 Chat 只用于历史展示，本机不能打开或复用其会话。
- Human Run 可以没有 Agent Run，也可以关联现有本机 Chat；这种关联只表示人工参考。
- Agent Review 的每个 attempt 使用新的 Chat 和 Run，不进入普通执行 Chat 的复用池；Human Review 由 Server 维护人工等待与 verdict。

同一 Issue 的活动 Agent Run 由 Server 协调。Desktop 收到运行或审查命令后，必须使用命令携带或 Server 准备的身份，不能自行拼装另一组 Issue、Stage、Agent、Chat 或设备关系。

## Kanban Chat 与 Copilot 边界

Kanban Chat 是 Agent WebClient 的独立 Root Observer，使用全局 Realtime Broker 的 Primary lane；它不改变 `issue.claim`、`issue.run.prepare`、Kanban native run 或 `run.event.append` 的身份和同步语义。Kanban 后台 runtime 是系统 request consumer，不伪装成 UI observer。

Issue detail 左侧通过 WebClient 的只读 Chat Preview 展示完整 Chat 历史和当前 Run，右侧继续由 Desktop 管理属性与运行记录。宿主从本机可打开的 Issue Chat 绑定 ownerChatId；URL 不授予身份或写权限。Preview 只允许读取自身 Chat、attach 及释放自身 observer，并只接收该 Chat 的 Push。切换 Chat 通过销毁旧 guest、注销旧 generation 后挂载新 guest；关闭详情或返回 Issue 正文释放 observer，不 interrupt 后台 Run。

Main Chat、Copilot Dock、Kanban Chat 的 live Root Observer 全局互斥。切换时先撤销旧观察身份并 detach，新的 Primary attach/query 等待旧 detach 完成；旧 generation 不得恢复观察。重新打开 Main Chat 由可信 Registry 重新建立 Root Observer 与 Overview lease。

Kanban route 不允许 Copilot Dock。AppShell 必须隐藏 Launcher 和 System Bar 入口、拒绝程序化 open/toggle，并在进入页面时让已有 Dock inactive 后卸载；Main 的 Surface Registry 对 Kanban context 的 Dock 注册再做一次 fail-closed 校验。持久状态中的 Kanban Dock session 被忽略或清除，其他页面的 Dock session 可以在离开 Kanban 后恢复。该限制不删除 Kanban Chat，也不削弱 Kanban 自身的运行能力。

## 终态结果未读

本地 Flow 最后阶段完成、自由任务完成，以及云端工作流最终状态产生结果未读。阅读身份以 Issue 与对应的 `chatId + runId` 为准；同一 Chat 的新 Run 重新产生未读，中间阶段和正在运行的结果不视为最终完成。

Desktop 在独立 state 文件中按当前用户和云端服务隔离保存阅读回执，不改写云端 Issue 或工作流，也不进入云端 mutation 协议。首次引入时，没有回执的已有终态任务显示未读；没有 Run 的人工结果使用完成时间或更新时间区分。重启后恢复回执。

详情的运行结果成功渲染且进入可见区域后才确认阅读；仅打开详情、加载中、加载失败、隐藏窗口及切换到聊天页均不触发此路径。关联本机 Chat 时必须验证 `lastRunContent` 对应精确 Run，由 Main 根据可信 Issue/Run/Device 关系调用 Platform `/api/read`，仅提交该 `chatId + runId`，复用 `chat.read` Push 更新 Chats 导航。无 Chat 时只记录本地回执；其他设备的 Chat 不能提交到本机 Platform。请求失败保留未读，再次展示结果可重试；迟到回执不得覆盖新 Run 或其他账号的阅读状态。

## 可靠性与恢复

- Cloud mutation、运行事件和已准备的手动运行身份分别持久化，避免一个队列承担不同一致性语义。
- 运行事件先写本地 outbox，再尝试发送；断线和重启后使用稳定事件 ID 重试。
- delivery、ACK、快照和增量事件都必须幂等；重复消息不能重复启动 Agent 或重复推进 Issue。
- 只有 Server 接受事件并返回权威更新后，Desktop 才以新的云端状态替换本地投影。
- Kanban 尚未发布，不保留历史配置、数据库、字段别名或浏览器偏好的兼容读取及自动迁移。普通读取不自动重写已有配置或修复旧数据库；新安装直接创建当前格式。当前格式的输入校验、缺省初始化与运行期恢复继续保留。
- 无法确认结果的中断运行不得猜测为成功；应保留可诊断状态并等待 Server 或后续同步收敛。

## 身份与安全

- Kanban 连接只使用 Desktop canonical SSO token；renderer 不持有或提交 JWT。设备名称由全局 Desktop profile 与系统设备信息提供，不再读取 Kanban 旧别名或将其导入 profile。
- Server 从已验证 token 和连接会话确定用户与设备，客户端 payload 不能覆盖身份。
- Agent 必须存在于目标 Desktop，用户必须具有目标 Project 权限。
- Cloud Issue 正文、评论、附件元数据和用户标识不得写入普通诊断日志；协议日志必须递归脱敏。
- Desktop Action 可以管理 Local Issue；Cloud Issue 仍受本节的受限原子操作约束。

## 实现事实源

- `src/main/modules/kanban/ws-client.ts`：连接、合同校验、握手和 delivery。
- `src/main/modules/kanban/runtime.ts`：同步编排、运行准备和事件回报。
- `src/main/modules/kanban/local-store.ts`：缓存、cursor、receipt、outbox 与当前 schema 初始化。
- `src/shared/contracts/kanban.ts`：跨进程 DTO。
- `test/fixtures/kanban-v1/` 与相关测试：精确协议形状和拒绝旧格式的边界。
