# 看板与云同步

当前对接协议为不兼容的 Contract 4.0 / WebSocket `v=4`。v3.2 与 v3.1 文档仅作为历史迁移参考，v4 Server 会明确拒绝旧协议客户端。

## 当前状态

Desktop Kanban 同时支持本地看板和云端权威缓存。Desktop 不把 cloud issue 当作可直接 CRUD 的公有 issue API；Contract 4.0 仅开放 `issue.claim`、Desktop 手动运行预登记 `issue.run.prepare`、人工本机 Chat 关联和 `run.event.append`。云同步引擎保留为 no-op 兼容壳，远端控制和云快照通过 Desktop Kanban WebSocket 客户端处理。

Server 以 `issueRunId + deviceId + externalRunId` 精确匹配运行事件；`chatId` 只是本机资源标识，不能单独定位运行。

## Contract 4.0 Worker、Chat 与 Run

- Worker 按 `(issueId, stageId, workerRole)` 保存，`workerRole` 分为执行节点 `run` 与审查节点 `review`。Agent Worker 同时固定 `agentKey + deviceId`；不同 Stage 不共享 Worker。
- 普通执行 Chat 按 `(issueId, deviceId, stageId, statusId, agentKey)` 建立复用池。只有完全相同节点、Agent 和 Desktop 的重做才默认复用首选 Chat；Stage/Status/Agent/设备变化、强制新对话或本地 Chat 丢失都会新建并替换首选。
- Agent Review 每个 attempt 强制新建 Chat 与 Run，Review Chat 永不成为首选。Human Run/Review 可以没有 Chat 和 Run；Human Run 可通过 `issue.chat.bind/unbind` 关联当前 Desktop 已有 Chat，记录为 `human_reference`。
- 每次 Agent 执行都创建新的 `issueRunId` 和 `externalRunId`，即使复用 Chat。同一 Issue 只允许一个活动 Agent Run。
- Snapshot 的运行详情来自 `issueStageWorkers[]`、`issueChats[]`、`issueRuns[]` 与 Review attempt。Issue 顶层不再提供 worker、Chat、Run、dispatch 标量；附件 `attachmentChatId` 保持独立。

## 核心流程

```text
Kanban UI / desktop action
  -> KanbanRuntime
  -> local SQLite store
  -> cloud issue.claim / issue.run.prepare / persistent run-event outbox
  -> normal assistant /api/query or automation create/update/delete
  -> desktop-nav frame=push run.started/run.finished
  -> run.event.append -> authoritative issue.updated
```

本地存储：

- legacy local store：`~/<brand>/.desktop/kanban.db`。
- v3 Desktop Kanban store：`data/desktop-kanban/kanban.db`。
- 新建 Local Issue 的本地主键使用 `local-<UPPER_BASE36_TICK>`：时间 tick 与 Server 一致取 `floor(epochMillis / 100)`，转大写 Base36；如 SQLite 中已存在则递增 tick 直到唯一。已有 `local_...` 长 ID 保持不变，不做主键迁移。
- Desktop Kanban 数据库 schema version 2 将 `syncMode` 收敛为 `local | cloud`。升级时会在同一事务中重建 `project` 与 `desktop_issue_sync` 的 CHECK 约束，并把旧 SQLite 行值 `private` 一次性迁移为 `local`；迁移完成后共享类型、IPC 对象和运行时不再接受 `private`。历史容器 ID `local-private-orphans` 与 Project `visibility="private"` 保持不变，前者是稳定身份，后者属于独立的可见性语义。
- 表结构包含 board、project、workflow、issue、review、event_log、desktop_issue_sync、project_desktop_binding 等。
- `kanban_cloud_mutation_outbox` 保存稳定 `issue.claim` mutation，`kanban_run_event_outbox` 保存带 `issueRunId/externalRunId` 的稳定运行事件，`kanban_manual_run_receipt` 保存 Server 预登记后的 `issueRunId/chatId/runId` 以支持重启恢复。
- 云端 Issue 的非核心详情字段保存在 `issue.DETAIL_JSON_`；用户、Issue 类型、动态字段定义/上下文/选项、工作流目录、标签关系、依赖、评审、评论和近期事件保存在按当前用户隔离的 `kanban_cloud_detail_cache`。完整 `project_set` 快照会替换这份详情缓存，增量 Issue 事件只更新对应 Issue，不清空目录数据。
- `dueDate` 是严格的 `YYYY-MM-DD` 日历日期，按原字符串缓存到 `issue.DETAIL_JSON_`，不得转换成 epoch 或附加时区。旧 `dueTime` 只取日期前缀，旧 `dueAt` 只在迁移读取时按原 Desktop 本地日历语义转换；新写入不再产生旧键。Server 计算的 `dueRisk` 只读缓存，本地 Local Issue 不复制风险算法。
- Project 通过 `versions` 和 `components` 维护版本、组件目录，分别缓存到 `project.VERSIONS_JSON_` 与 `project.COMPONENTS_JSON_`。Issue 使用 `projectVersion` 与 `componentKeys`；旧 `version` 只作为 Desktop Action/存量详情兼容输入。Website 和 Desktop 原生表单均从所属 Project 目录选择，云端 Issue 继续保持只读。
- Issue 的 `resolution`、`securityLevelKey`、`reporterId`、`originalEstimate`、`remainingEstimate`、`timeSpent` 与上述日期/目录字段都随完整快照和单 Issue 增量实体写入详情缓存；工时统一使用非负整数秒。`securityLevelKey` 在原生 UI 只读，Desktop Action 可为 Local Issue 设置；`dueRisk` 不可写。
- 云端 `priority` 的 `urgent/high/medium/low` 在 Desktop 缓存边界映射为 `P0/P1/P2/P3`，Desktop Action 同时接受两种输入、输出仍使用 P0–P3。`priority` 与 `severity` 都允许为空，不再补 `P2` 或 `medium`。
- Issue Card 顶边使用 3px 工作流进度轨，优先采用当前 Stage 的目录 `color`，缺失时使用稳定语义色板。Issue Type 在左上角显示低饱和度竖线与实心图标；Project 和 `projectVersion` 分开显示，Todo 排序号位于顶部状态区。标题前的优先级/重要程度使用一个合并标识：优先显示优先级文字，未设置优先级时才显示重要程度文字，标识颜色始终由重要程度决定；两者都缺失时不渲染，完整信息保留在 tooltip。Footer 固定为人员在左、时间或截止信号在右；Local Issue 的 assignee 隐含为当前用户，卡片不重复显示 assignee，只显示实际存在的 Worker，Cloud Issue 继续按 assignee 与 Worker 语义展示。Todo 始终显示未设置/今天/未来/逾期四类日期信号，其他未完成状态显示更新时间，Completed 显示完成更新时间。时间区域只显示紧凑时间值，不显示 `Updated`、`Completed`、`更新`、`完成` 等前缀，具体时间语义保留在 tooltip。Server 提供 `dueRisk` 时显示可减少动态效果的红色闹钟；第二行只显示失败、取消、等待审批等异常状态，不重复运行中。卡片不提供聊天或删除悬浮按钮；点击进入详情，聊天保留在详情头部，本地删除保留在详情和右键菜单。

远端控制：

- WS URL 由 `serverUrl` 派生 `/ws`。
- role 固定为 `desktop`，协议版本当前为 `v=4`、Contract `4.0`。
- token 来自环境变量或 SSO site token。
- 支持 snapshot、delivery、issue events、受限 `issue.claim`、`issue.run.prepare`、`issue.chat.bind/unbind`、`run.event.append`、`command.runIssue`、`command.reviewIssue`、list agents、start run、automation sync、local project binding。
- 云连接状态区分前置条件：未填写 Server URL、未启用 Kanban 或未开启远程控制时显示“未配置”；配置完整但 Desktop SSO 凭证尚未就绪、site token 缺失或已过期时显示“请重新登录”，不再将凭证问题误报为未配置。重新登录生成有效 site token 后自动刷新连接状态。

## 日志与排障

Kanban Server WebSocket 由 Desktop 主进程建立，因此不会显示在 renderer DevTools 的 Network 面板。连接、关闭、错误，以及每一条收发帧都会独立写入 JSONL 日志：`~/<brand-runtime-root>/.desktop/logs/desktop/kanban-ws.log`（Windows 为 `%USERPROFILE%\\<brand-runtime-root>\\.desktop\\logs\\desktop\\kanban-ws.log`）。Settings → Debug → Desktop Logs 的 **Kanban WS Log** 会在独立浮层中实时查看该文件，不与 Desktop `main.log` 混合。

每一行包含时间、连接诊断或收发方向、字节数与完整协议帧。token、authorization/cookie/secret/password/API key、敏感 URL 查询参数、本机绝对路径与 Local Issue 内容会递归替换为脱敏标记。文件固定为一个路径，超过 10 MiB 时只保留最近的完整日志行。

桌面动作：

- `desktop.kanban.listIssues`
- `desktop.kanban.getIssue`
- `desktop.kanban.createIssue`
- `desktop.kanban.updateIssue`
- `desktop.kanban.deleteIssue`
- `desktop.kanban.moveIssue`

Renderer IPC 另提供 `kanban.claimIssue(issueId)` 与 `kanban.runIssue({ issueId, agentKey, forceNewChat? })`；它们不是 Desktop Action 公共 CRUD。

## 约束与注意事项

- cloud Kanban issue 的正文和工作流状态在 Desktop UI/runtime 中保持只读；“认领”只写 assignee，“开始处理”先向 Server 预登记 `issueRunId`，再通过正常 Chat 与运行事件推进。
- 卡片默认 `width: 100%` 撑满所在列，最小宽度为 `200px`；列内容区顶部 padding 与卡片间 gap 均为 `4px`，左右和底部 padding 为 `8px`，横向滚动时单列最窄为 `216px`。五列外层不保留 padding，Kanban 最小内容宽度为 `1080px`。亮色 Column 使用 `#F3F4F6`、白色 Issue Card；暗色 Column 使用 `#212121`，Issue Card 及拖拽镜像统一使用 `#181818`。卡片按真实内容自然增高，顶边 Stage 工作流进度轨固定为 `3px`。项目、独立版本标签与顶部细分 Status 使用紧凑整数像素字号；长标题、版本和人员在 200px 卡片中截断。键盘焦点作用于整张卡片。Issue 不包含 `reviewerId` 或 Issue 级 `reviewRequired`；审核由工作流 Status 表达。所有构建只展示实体与目录中实际存在的数据，不生成演示人员、不补默认等级或 Project/Issue Type。
- Kanban 操作反馈使用底部居中的轻量 toast，宽度随内容变化且不超过 `360px`，避免遮挡列顶部新建的 Issue。成功提示 3 秒后自动关闭，悬停时暂停计时；错误提示保留至用户手动关闭。
- 仅 Todo 列支持在卡片之外的列内容空白处双击新增 Issue；Todo 为空时，投放区显示“双击此处新增问题”的操作提示。其他状态列不显示该提示，也不响应空白处双击新增。
- Project 筛选弹层复用侧栏操作菜单的主题玻璃样式：半透明背景、背景模糊与饱和、细边框、内高光阴影及 hover 色在亮暗主题下保持一致，不使用 Kanban 专属不透明底色。垂直滚动条使用 8px 单轨样式，轨道以接近弹层底色的遮罩隔离背后 Kanban 分隔线，避免滚动条旁出现两条竖线。菜单在“全部项目”下提供独立的“本地”来源块，以来源色条、轻背景和项目树分隔线区别普通 Project；“不会上传云端”作为名称右侧的次级说明。该选项只匹配 `syncMode=local` 的 Local Issue，普通 Project 选项只匹配对应云端只读缓存。两类选项可多选并按并集展示，“全部项目”仍展示本地与云端全集。Project checkbox 使用标准级联树语义：勾选或取消父项目会同步作用于全部后代；单独改变后代后逐级重算祖先，部分后代选中时显示半选、全部直接子项完整选中时显示完整选中；点击半选父项目会选中整棵子树。选择 2 个及以上范围时，hover 或键盘聚焦仅显示已选清单；每项显示一行，Project 可附带父级路径，不重复 Issue 数量或“已选 N 项”摘要。展开菜单时隐藏该提示，并在“本地”和每个 Project 行右侧显示各自 Issue 数；父项目按筛选语义汇总自身及全部后代云端 Issue，叶子项目显示自身云端 Issue 数。
- New Issue 的 Project 默认选择“本地”，并继续以 `syncMode=local` 保存在 Desktop；用户可改选项目目录中的任意真实 Project。Project 自定义下拉最高为 `240px`，超出后在菜单内部滚动；项目按树层级缩进但不使用不可选的分组标题，父 Project 与叶子 Project 都是可直接选择的 Issue 容器。未指定 Project 的本地 Issue 仍以默认本地容器持久化。
- 右上角视图设置使用齿轮图标，只控制 Backlog（中文“待排期”）列是否显示，不控制 Priority 等卡片字段。隐藏 Backlog 只改变当前看板布局，不删除或修改其中的 Issue；显示状态与其他 Kanban 筛选偏好一并保存在 renderer 本地，切换页面、刷新和重启 Desktop 后恢复上次选择，再次显示后恢复该列及其原有内容。设置弹层点击自身保持打开，点击弹层和入口之外的区域时关闭。
- Search issues 增加 Issue Type 多选，菜单只展示 `isActive !== false` 的有效类型；优先级和重要程度筛选都提供“未设置”，并可与 Project、负责人和自动化筛选组合。全文索引包含类型、组件、Reporter、负责人/执行者 ID、Project ID/名称/路径、版本及附件名。搜索词、Project 与本地来源、Issue Type、优先级、重要程度、自动化和负责人统一保存在 renderer 本地筛选偏好中，离开 Kanban、刷新页面和重启 Desktop 后完整恢复；项目目录成功加载前不得清理已保存的 Project 选择。负责人筛选使用“他人 / 自己 / 未分配”三项多选，按云端 `assigneeId` 与当前用户 ID 判定；首次使用时系统默认仅选择“自己”，旧版独立负责人筛选偏好会迁移到统一偏好。
- `/kanban` 的 Issue Detail 使用固定的内容/属性双栏：桌面端最大尺寸为 `1062px × 738px`，右栏固定为 `280px`，左栏使用剩余宽度；头部只在云端 Issue 显示 Cloud 来源；左侧紧凑展示 Title、Markdown Description、附件列表和逐条评论。Description 在只读态直接渲染安全的 GFM Markdown 预览，进入本地编辑态后才显示 Markdown 原文 textarea；编辑器根据实际文字内容及可用宽度自动增高，自身不显示纵向滚动条。Description 与 Comments 的 Markdown 图片允许受限的 base64 raster 与 `image/svg+xml` Data URL，SVG 仍通过 `<img>` 隔离显示，不以内联 HTML 执行；`mermaid` 围栏代码块按需加载 Mermaid 并渲染图表，使用严格安全级别禁用图表内点击脚本和原始 HTML；非法语法降级显示原始代码，不影响其余 Markdown；Website 使用相同 Mermaid 配置。右栏顶部提供吸顶锚点导航，并只保留基本属性、负责人、关联、时间线四组。云端 Issue 全部只读，但未认领 Todo 可执行“认领”，本人已认领 Todo 可执行“开始处理”；本地 Issue 默认只读打开，可编辑 Title、Description、日期型截止日期、项目版本、Resolution、Components、Reporter、三类工时、可空优先级/重要程度、状态、执行 Agent、自动化和附件。Basic 同时只读展示 `dueRisk` 与 `securityLevelKey`，Project/Issue Type/Workflow/Stage 和云端动态字段不在 Desktop 管理。聊天和本地 Issue 的编辑入口位于详情右上角、关闭按钮左侧；查看聊天会把当前弹窗原位切换为临时 Agent WebClient，右上角可切回问题详情，关闭或返回详情时卸载该 WebView；弹窗聊天不接管外层主 Chat 路由。本地删除位于 Basic 底部。Settings 中 Debug、双击复制、安全 Markdown、关联、时间线与窄屏响应式规则保持不变。
- Issue Detail 的 Markdown 图片允许 HTTPS URL，包含远程 `image/svg+xml`；HTTP URL 继续由 CSP 禁止，远程 SVG 仅作为 `<img>` 图片加载，不获得脚本或内联 HTML 执行能力。
- 不调用已移除的 public issue CRUD / review / label / dependency 端点。
- `run.event.append` 是 Desktop runtime 同步 Run/Review 终态的协议，不是 public issue CRUD；必须携带 `issueRunId + deviceId + externalRunId`。
- Cloud 终态只按 Server 创建的运行三元组关联；不得仅凭相同 `chatId` 修改 Issue。`clientEventId` 固定由 device、issueRun、externalRun 和 event type 生成。
- Kanban 生命周期的唯一事实源是 `desktop-nav` WebSocket 已验证的 `frame="push"`。`response`、`error`、`stream`、普通 push、`run.activity` 和 `/api/query` SSE 均不得触发 Kanban 写回；SSE 只用于聊天内容与完整错误详情。
- Kanban 只允许 `run.started` 与 `run.finished`，并且只按当前精确 `runId` 关联。`run.finished` 的合法映射固定为 `completed + complete` → Local Completed / Cloud `run.completed`，`failed + error` → Local Todo / Cloud `run.failed`，`interrupted + cancel` → Local Todo / Cloud `run.cancelled`。缺少 `finishReason`、未知值或冲突组合一律诊断后忽略，绝不默认完成。
- Local 终态在主进程写库后发送 `kanban.changed`，Renderer 只重新读取主进程数据，不再订阅 assistant SSE 重复更新。Cloud Issue 的列保持 Server 权威只读，Desktop 仅写三类 terminal outbox，等待 `issue.updated` 收敛；失败和取消自动回 Todo 均不触发重试。
- Local Issue 由用户主动移入 Todo 后延迟 1 秒执行一次；Completed 返工优先复用 Issue 原 `chatId`，但每次执行都生成新 `runId`。失败或取消造成的自动回 Todo 不触发重试。
- 用户界面、共享契约与 SQLite 统一使用“本地问题 / Local Issue”及 `syncMode="local"`；`private` 仅存在于旧数据库迁移输入和独立的 Project visibility 语义中。
- 非拖拽完成任务有保护逻辑，避免普通更新直接把 issue 标记为 completed。
- automation 同步走 agent-platform `/api/automation/create`、`/api/automation/update`、`/api/automation/delete`。
