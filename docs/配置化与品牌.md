# 配置化与品牌

## 文档定位

本文描述多品牌构建、配置来源和隔离原则。品牌字段、环境变量、默认值和生成文件格式以品牌 schema、源码与构建脚本为准。

## 品牌模型

品牌配置是产品身份的源，定义应用名称、app id、存储命名空间、外部协议、运行目录、图标、本地化和平台安装属性。

```text
brands/<brand>/ 源配置
  -> 品牌校验与资源生成
  -> build/brands/<brand>/generated
  -> Electron 构建与运行时 APP_BRAND
  -> 路径、协议、文案、图标和安装器
```

生成目录可以重建，不接受手工修改。新增或修改品牌应从品牌源开始，并通过同一生成流程同时覆盖 main、renderer 和平台构建。

## 配置分层

Desktop 配置按所有者分层：

| 配置 | 权威来源 | 说明 |
| --- | --- | --- |
| 品牌身份 | `brands/<brand>/` | 构建期与运行期共同使用 |
| Desktop canonical 配置 | Desktop 数据根的 `config/desktop` | Desktop 自己解释和维护 |
| 服务配置 | 各服务配置根 | 服务 deploy 解释和迁移 |
| 插件配置 | 插件隔离配置根 | 插件 schema 与宿主管理共同约束 |
| 用户偏好 | Desktop profile 或领域 store | 不能写回品牌源和发布包 |
| 敏感凭据 | secrets、Electron session 或专用状态 | 不进入品牌文件、文档和日志 |

构建或开发环境变量只选择品牌、资源输入和平台构建行为，不应成为运行时业务配置的隐藏第二来源。

## 隔离原则

- 不同品牌使用不同 app id、协议、运行根、程序数据根和 Electron partition 命名空间。
- 一个品牌不能读取、迁移或删除另一品牌的数据。
- 外部唤起协议必须由品牌源显式声明，不能从显示名称猜测。
- Help、SSO、Website、WebApp 和插件存储都继承品牌命名空间，但仍保留各自 partition 边界。
- 真实 token、证书、私钥和本机 `.env` 不进入品牌源或生成物。

## 平台差异

macOS 与 Windows 分别生成图标、安装器元数据、权限说明和目录配置。原生系统面板使用操作系统语言；Desktop 内部语言设置只控制应用自身界面，不能伪装成系统语言覆盖。

平台特有值必须在品牌 schema 中显式表达，不能依赖某个平台忽略未知字段的偶然行为。

## 变更规则

- 修改品牌源后运行统一生成与校验流程。
- 生成产物漂移应由检查失败暴露，不在产物上直接修补。
- 新增品牌必须补齐必需图标、本地化、目录和协议身份。
- 影响用户数据位置或外部协议的品牌变更属于兼容性变更，需要同时评估升级和卸载。

## 实现事实源

- `brands/` 下各品牌源文件
- `scripts/lib/brand-config.mjs` 与 `scripts/sync-brand.mjs`
- `src/shared/brand.ts`
- `src/main/user-paths.ts`
- 品牌生成、运行路径、协议和平台安装测试
